# M3.4.3 — Tool System Specification

**Status:** Accepted
**Date:** 2026-07-12
**Dependencies:** M3.4.1 (Editor Interaction), M3.4.2 (Selection System), ADR 0015 (Service Boundaries)

---

## 1. Purpose

NAVI Studio has two parallel tool systems: a service-based `ToolRegistry` with clean `Tool` interface objects, and a legacy `InteractionController` that implements all tool behavior inline via Zustand. The two systems do not communicate — tools registered via `ToolRegistry` receive no pointer events, and the `InteractionController`'s hardcoded behavior is invisible to the service layer.

M3.4.3 defines the unified tool architecture. It specifies how tools are authored, registered, activated, and how pointer/keyboard events route from the map to the active tool. It defines the tool lifecycle contracts (including Preview/Confirm), the hit-test system, and the migration path from the inline InteractionController to the Tool interface.

---

## 2. Tool Principles

1. **Tools are behavior modules, not application modes.** A tool changes how input is interpreted, not what the editor is doing. Multiple UI consumers (Canvas, Status Bar, Context Panel) can remain unaware of which tool is active — they only react to selection and document state.
2. **Exactly one primary tool is active at any time.** The `ToolRegistry.activeToolId` is always set. The editor never exists in a "no tool" state.
3. **Tools receive events, not raw map callbacks.** The `InteractionController` routes map events to the active tool's `onPointerDown/Move/Up/KeyDown` methods. No tool behavior is hardcoded in the event router.
4. **Tools own temporary interaction state.** A drawing tool may accumulate vertices during a drag. A select tool may track hover state via `PointerManager`. This state is reset on `onDeactivate()` or when the tool completes its operation.
5. **Tools never own document state.** Only `CommandDispatcher` may mutate `CampusDocument`. Tools collect input, enter Preview, and dispatch commands on confirm.
6. **Only mutating tools enter Preview.** Tools that modify the document (draw, place, edit) must enter a Preview state before a command can be dispatched. Non-mutating tools (select, pan) skip Preview.
7. **Selection survives tool changes.** Activating a new tool never clears the selection set. This is enforced at the `ToolRegistry.activate()` level — no tool may call `selection.clear()` during `onActivate()`.

## 3. Tool Architecture

```
MapLibre Map Events
        │
        ▼
InteractionController (router only)
        │
        ├─ mouse/pointer → Tool.onPointerDown/Move/Up
        ├─ keyboard      → Tool.onKeyDown
        └─ hit-test      → SpatialQueryService
                │
                ▼
         Active Tool
                │
                ├─ Non-mutating (select, pan)
                │       └─ update SelectionManager / PointerManager
                │
                └─ Mutating (draw, place, edit)
                        │
                        ├─ collect input → accumulate state
                        ├─ enter Preview → PreviewManager.publish()
                        ├─ Confirm       → PreviewManager.confirm()
                        └─ Cancel        → PreviewManager.cancel()
```

Four layers, strictly separated:

| Layer | Responsibility | Never Does |
|---|---|---|
| **InteractionController** | Route events, manage cursors, provide hit-test results | Implements tool behavior, owns selection |
| **Active Tool** | Interpret input, accumulate state, decide to Preview or commit | Mutate document, own selection |
| **PreviewManager** | Own preview state, geometry, confirm/cancel lifecycle | Interpret input, own document state |
| **CommandDispatcher** | Execute validated commands against CampusDocument | Interpret input, own tool state |

### PreviewManager (New Service)

`PreviewManager` is a shared service that owns all preview state. Tools publish to it; Canvas, Context Panel, and ConfirmBar read from it.

```typescript
class PreviewManager extends BaseEditorService {
  readonly id = 'preview'
  readonly dependencies = ['eventBus']

  /** Current preview state. Null when no preview is active. */
  get current(): PreviewState | null

  /** Whether a preview is currently active. */
  get isActive(): boolean

  /** Publish a preview payload. Called by the active tool when accumulation completes. */
  publish(state: PreviewPayload): void

  /** Update preview geometry (tool accumulated another vertex). */
  update(state: Partial<PreviewPayload>): void

  /** Confirm the current preview — dispatches the command and clears state. */
  confirm(ctx?: ToolContext): void

  /** Cancel the current preview — clears state without dispatching. */
  cancel(): void

  /** Clear preview without emitting events (used during tool deactivation). */
  reset(): void
}

interface PreviewPayload {
  toolId: string
  commandId: string
  label: string
  payload: Record<string, unknown>
  previewGeometry?: GeoJSON.Feature
}

interface PreviewState {
  toolId: string
  commandId: string
  label: string
  payload: Record<string, unknown>
  previewGeometry: GeoJSON.Feature | null
}
```

PreviewManager emits:

| Event | Payload | Description |
|---|---|---|
| `preview.changed` | `PreviewState` | Preview state updated (new vertex, geometry change) |
| `preview.confirmed` | `{ toolId, commandId }` | User confirmed — command dispatched |
| `preview.cancelled` | `{ toolId }` | User cancelled — state cleared |

### Tool → PreviewManager Flow

```
Tool.onPointerDown (accumulates vertex)
    │
    ├─ tool finished accumulation (min vertices met, Enter pressed)
    │       │
    │       └─ PreviewManager.publish({ toolId, commandId, label, payload, previewGeometry })
    │               │
    │               ├─ emit preview.changed
    │               ├─ Canvas reads → renders preview overlay
    │               ├─ Context Panel reads → shows ConfirmBar
    │               └─ Status Bar reads → shows "Preview: Create Room"
    │
    └─ tool still accumulating
            │
            └─ PreviewManager.update({ previewGeometry })
                    │
                    └─ emit preview.changed → Canvas re-renders overlay

ConfirmBar "Create Room" clicked
    │
    ├─ PreviewManager.confirm(ctx)
    │       │
    │       ├─ ctx.services.dispatcher.execute({ id: commandId, payload })
    │       ├─ emit preview.confirmed
    │       ├─ reset internal state
    │       └─ tool stays active or switches to select
    │
    └─ PreviewManager.cancel()
            │
            ├─ emit preview.cancelled
            ├─ reset internal state
            └─ tool clears accumulation state
```

This separation means tools never own the preview lifecycle. They only call `PreviewManager.publish()`/`update()`/`cancel()`. The Canvas and Context Panel read from `PreviewManager.current`, not from the active tool.

### Event Routing Contract

```
map.on('click', (e) => {
    const toolEvent = normalizeToToolEvent(e)
    const ctx = makeToolContext(services)
    activeTool.onPointerDown(toolEvent, ctx)
})
```

The `InteractionController` normalizes all pointer input (mouse, touch, pen) into `ToolPointerEvent`. It never branches on tool ID — it calls `activeTool.onPointerDown()` unconditionally. The active tool decides what to do.

### Exceptions

Two exceptions to the "unconditional routing" rule:

1. **Space+Pan override** — When Space is held, `InteractionController` temporarily activates the Pan tool regardless of `activeToolId`. On Space release, it reactivates the previous tool. This is the only override mechanism.
2. **Marquee drag** — When the Select tool emits a marquee drag start, the `InteractionController` captures the drag and routes `onPointerMove`/`onPointerUp` to the Select tool's marquee handlers. No other tool needs drag capture.

## 4. Tool Interface (Revised)

```typescript
interface Tool {
  /** Unique tool identifier (kebab-case). */
  id: string

  /** Human-readable label for UI display. */
  label: string

  /** CSS cursor when this tool is active. */
  cursor?: string

  /** Tool category — determines Preview behavior. */
  kind: 'select' | 'navigate' | 'create' | 'modify' | 'utility'

  /** Whether this tool enters Preview state before dispatch. */
  isMutating: boolean

  /** When true, InteractionController disables map.dragPan while this tool is active. */
  blocksMapDrag?: boolean

  /** Workspace contexts this tool is valid in. Empty = all contexts. */
  validIn?: EditorMode[]

  // ── Lifecycle ──────────────────────────────────────────────

  onActivate?(ctx: ToolContext): void
  onDeactivate?(ctx: ToolContext): void

  // ── Input ──────────────────────────────────────────────────

  onPointerDown?(event: ToolPointerEvent, ctx: ToolContext): void
  onPointerMove?(event: ToolPointerEvent, ctx: ToolContext): void
  onPointerUp?(event: ToolPointerEvent, ctx: ToolContext): void
  onDblClick?(event: ToolPointerEvent, ctx: ToolContext): void
  onKeyDown?(event: KeyboardEvent, ctx: ToolContext): void
}
```

### ToolContext Contract

`ToolContext` is the official contract for what every tool can access. It is provided by the `InteractionController` on every input event.

```typescript
interface ToolContext {
  /** Typed access to all editor services. */
  services: ServiceAccessor

  /** Shortcuts to the most commonly accessed services.
   *  Every tool relies on at least one of these. */
  get selection(): SelectionManager
  get pointer(): PointerManager
  get preview(): PreviewManager
  get dispatcher(): CommandDispatcher
  get viewport(): ViewportManager
  get eventBus(): DocumentEventBus
  get toolRegistry(): ToolRegistry
  get spatial(): SpatialQueryService
  get editingContext(): EditingContextService
}
```

Concretely, these resolve to `services.get('selection')`, `services.get('pointerManager')`, etc. The shorthand properties exist so tool authors do not need to remember service registry IDs.

A tool author writing a new tool can assume these services are always available:

| Shorthand | Service ID | Always Available? |
|---|---|---|
| `selection` | `selection` | Yes |
| `pointer` | `pointerManager` | Yes |
| `preview` | `preview` | Yes |
| `dispatcher` | `dispatcher` | Yes |
| `viewport` | `viewport` | Yes |
| `eventBus` | `eventBus` | Yes |
| `toolRegistry` | `toolRegistry` | Yes |
| `spatial` | `spatialQuery` | Yes |
| `editingContext` | `editingContext` | Yes |

### ToolKind Semantics

| `kind` | Mutating? | Preview? | Examples |
|---|---|---|---|
| `select` | No | No | Select, Marquee |
| `navigate` | No | No | Pan, Zoom |
| `create` | Yes | Yes | Draw Building, Place Entrance |
| `modify` | Yes | Yes | Vertex Edit, Move (M3.5) |
| `utility` | No | No | Calibrate |

### What Changed from M3.4.1

| Change | Rationale |
|---|---|---|
| Added `kind` field | Enables UI consumers to categorize tools without instanceof checks |
| Added `isMutating` field | Determines whether Preview is required |
| Added `blocksMapDrag` field | Replaces hardcoded dragPan disable in InteractionController |
| Added `validIn` field | Enables context validation when editing mode changes |
| Added `onDblClick()` | Double-click is semantically distinct from single-click (route completion) |
| Removed `buildPreview()` | Preview lifecycle moved to PreviewManager — tools call `preview.publish()` |
| Removed `onConfirm()` | Tool calls `PreviewManager.confirm()` instead |
| Removed `onCancel()` | Tool calls `PreviewManager.cancel()` instead |
| Removed `renderPreview()` | Canvas reads `PreviewManager.current.previewGeometry` directly |
| Added `ToolContext` contract | Defined precisely what every tool can access |

## 5. ToolRegistry (Revised)

```typescript
class ToolRegistry extends BaseEditorService {
  readonly id = 'toolRegistry'
  readonly dependencies = ['selection', 'viewport', 'dispatcher', 'eventBus']

  // ── Registration ───────────────────────────────────────────

  register(tool: Tool): void
  registerMany(tools: Tool[]): void
  remove(id: string): void

  // ── Activation ─────────────────────────────────────────────

  activate(id: string, ctx?: ToolContext): void

  /** Temporarily override with a different tool. Stores the previous tool ID for restoration. */
  override(id: string, ctx?: ToolContext): void

  /** Restore the tool that was active before the most recent override(). */
  restore(ctx?: ToolContext): void

  /** Force-deactivate without tracking (used during editor shutdown). */
  deactivate(ctx?: ToolContext): void

  // ── Queries ────────────────────────────────────────────────

  get(id: string): Tool | undefined
  get activeTool(): Tool | null
  get activeToolId(): string | null

  /** The tool that was active before the current override. Null if no override is active. */
  get overriddenToolId(): string | null

  /** All registered tools, keyed by kind. */
  get byKind(): Partial<Record<ToolKind, Tool[]>>

  get all(): Tool[]
}
```

### Activation Flow

```
toolRegistry.activate('draw-building')
    │
    ├─ 1. Read activeTool: if already 'draw-building', no-op.
    ├─ 2. Call activeTool.onDeactivate(ctx) (if any)
    ├─ 3. Update _activeId = 'draw-building'
    ├─ 4. Call newTool.onActivate(ctx)
    ├─ 5. If newTool.isMutating: enter Preview mode
    ├─ 6. Emit tool.changed { toolId: 'draw-building', kind: 'create' }
    └─ 7. Clear PointerManager hover state (optional — tool may want it)
```

### Override Flow

```
Space key down
    │
    ├─ InteractionController detects Space held
    ├─ toolRegistry.override('pan', ctx)
    │       ├─ stores activeToolId in overrideStack
    │       ├─ calls activeTool.onDeactivate()
    │       └─ calls panTool.onActivate()
    └─ map.dragPan.enable() (Pan tool sets cursor = grab)

Space key up
    │
    ├─ InteractionController detects Space released
    └─ toolRegistry.restore(ctx)
            ├─ calls panTool.onDeactivate()
            ├─ pops overrideStack
            └─ calls previousTool.onActivate()
```

### Activation Invariants

- `activate()` with the current tool ID is a no-op.
- `activate()` on an unregistered ID throws `Error`.
- `override()` can stack (e.g., Space during a momentary tool).
- `restore()` with an empty stack is a no-op.
- `deactivate()` leaves `activeToolId` as `null`. Only called during editor shutdown.

## 6. Preview / Confirm Cycle

For `isMutating === true` tools, all mutations go through a Preview → Confirm → Command pipeline.

```
Accumulate input (vertices, position, properties)
        │
        ▼
Finish accumulation (Enter key, DblClick, explicit "Complete" action)
        │
        ▼
Enter Preview
        │
        ├─ buildPreview() → PreviewPayload { commandId, payload, previewGeometry }
        ├─ emit preview.changed { payload, previewGeometry }
        ├─ Canvas renders previewGeometry as dashed/temporary overlay
        ├─ Context Panel shows ConfirmBar with "Create Room" / "Cancel"
        │
        ├─ Confirm
        │       │
        │       ├─ onConfirm(ctx)
        │       │       └─ dispatcher.execute() → entity.created event
        │       ├─ emit preview.confirmed
        │       ├─ exit Preview
        │       └─ tool stays active (for creation tools) or switches to select
        │
        └─ Cancel
                │
                ├─ onCancel(ctx)
                │       └─ clear accumulated state
                ├─ emit preview.cancelled
                ├─ Canvas clears preview overlay
                └─ tool stays active (accumulation resets)
```

### Preview Event Types

| Event | Payload | Description |
|---|---|---|
| `preview.changed` | `{ toolId, payload, previewGeometry }` | Preview state updated (new vertex added, etc.) |
| `preview.confirmed` | `{ toolId, commandId }` | User confirmed — command was dispatched |
| `preview.cancelled` | `{ toolId }` | User cancelled — state cleared |

### What Triggers Preview Entry

- **Drawing tools** (draw-room, draw-building, draw-road, draw-hallway): Enter key or DblClick when vertex count meets minimum.
- **Placement tools** (place-entrance, etc.): Auto-enter Preview on first click for single-click placement, or accumulate if the tool allows multi-placement.
- **Modification tools** (future): On confirm after handle manipulation.

### What Triggers Preview Exit

- **Confirm**: User clicks Confirm in ConfirmBar, or presses Enter when ConfirmBar is visible.
- **Cancel**: User clicks Cancel, presses Escape, or switches to a different tool.

## 7. SpatialQueryService

`entityAtEvent()` is a critical missing piece. Currently a stub returning `null`. The `SpatialQueryService` replaces the narrow `HitTestService` with a general purpose spatial query layer that will grow to support snapping, collision detection, and marquee selection.

```typescript
interface SpatialQueryService {
  /** Find the topmost entity at the given screen position. Returns selector and metadata. */
  entityAtEvent(point: { x: number; y: number }, map: Map): HitTestResult | null

  /** Find all entities within a bounding rectangle (for marquee selection). */
  entitiesInBounds(bounds: BBox, map: Map): HitTestResult[]

  // ── Future methods (M3.5+) ─────────────────────────────────

  // nearestVertex(point, map)
  // nearestRoad(point, map)
  // entitiesInsidePolygon(polygon, map)
  // snapTargets(point, map, filter?)
  // collisionDetection(newGeometry, map)
}

interface HitTestResult {
  selector: EntitySelector
  entityId: string
  layer: string
  /** Distance from click point to entity center — for disambiguation. */
  distance: number
}
```

### Hit-Test Priority

Vertices > Selection/transform handles > Entity nodes > Entrances > Roads > Rooms > Buildings > Campus boundary > Background

(M3.4.1 Section 2 specifies this ordering. `SpatialQueryService` implements it.)

### Ownership

- `SpatialQueryService` is a service, registered in `ServiceRegistry` alongside `SelectionManager` and `PointerManager`.
- It is consumed by the Select tool, `PointerManager` (for hover detection), `PreviewManager` (for preview geometry validation), and any tool that needs spatial queries.
- It does **not** cache results — each call performs a fresh query against the map's rendered features.
- Future methods (snapping, collision detection) will be added as the service grows in M3.5+.

### Integration with PointerManager

`PointerManager` calls `SpatialQueryService.entityAtEvent()` on every `onPointerMove` and updates its `hoveredSelector`/`hoveredEntityId` accordingly. The Select tool reads this during `onPointerDown` to decide whether to select or clear.

## 8. Tool Authoring Contract

### Tool State

Tools must **not** use module-level mutable state:

```typescript
// ❌ Bad — shared global state
let active = false
let vertices = []
```

```typescript
// ✅ Good — state scoped to activation
class DrawBuildingTool implements Tool {
  private active = false
  private vertices: LatLng[] = []

  onActivate(): void {
    this.active = true
    this.vertices = []
  }
  // ...
}
```

### Tool Registration

Tools are registered during editor context creation:

```typescript
// In configure-default-tools.ts
toolRegistry.registerMany([
  selectTool,
  panTool,
  drawBuildingTool,
  drawRoadTool,
  drawRoomTool,
  drawHallwayTool,
  placeEntranceTool,
  placeStaircaseTool,
  placeElevatorTool,
  placePanoramaTool,
  placeQrTool,
])
```

Floor-specific tools are registered in `configure-floor-editor-tools.ts` (already exists).

### Tool Dependencies

Tools access services through `ToolContext.services`. The services a tool typically needs:

| Service | Used For |
|---|---|---|
| `selection` | Select tool — select/toggle/clear |
| `pointerManager` | Hover state, modifier keys |
| `preview` | All mutating tools — publish preview state |
| `dispatcher` | All mutating tools — dispatch commands |
| `viewport` | Floor/building context for creation tools |
| `spatialQuery` | Select tool — entityAtEvent; PointerManager — hover detection |
| `eventBus` | Emit tool-specific events |
| `editingContext` | Validate tool against current editing mode |

## 9. InteractionController (Routed Architecture)

The current `InteractionController` (366 lines, hardcoded tool behavior) is refactored into a thin router.

### Before (Current)

```
InteractionController.tsx (366 lines)
    ├─ list of refs for all Zustand state
    ├─ handleClick: big switch on curTool → inline behavior
    ├─ handleMouseDown: big switch on curTool → inline behavior
    ├─ handleMouseMove: big switch on curTool → inline behavior
    ├─ handleMouseUp: big switch on curTool → inline behavior
    ├─ handleKeyDown: big switch on curTool → inline behavior
    └─ useEffect: cursor + dragPan management
```

### After (Target)

```
InteractionController.tsx (~80 lines)
    ├─ useEffect: register map event listeners
    ├─ normalizeEvent(e) → ToolPointerEvent
    ├─ Forward to activeTool.onPointerDown/Move/Up
    ├─ Space key: toolRegistry.override('pan') / restore()
    ├─ Cursor: read activeTool.cursor
    └─ DragPan: read activeTool.blocksMapDrag (new property)
```

### Migration

| Step | What | Phase |
|---|---|---|
| 1 | Add `blocksMapDrag` to Tool interface | M3.4.3 |
| 2 | Implement `HitTestService` | M3.4.3 |
| 3 | Rewrite `InteractionController` as router | M3.4.3 |
| 4 | Migrate hardcoded tool behavior into Tool objects | M3.4.3 |
| 5 | Remove Zustand tool state (`useStudioStore.tool`) | M3.4.4 |
| 6 | Remove `InteractionController` inline handlers | M3.4.4 |

## 10. Tool Activation Sources

All tool activation flows through `CommandDispatcher`. This ensures a single activation path consistent with the "Commands are the only mutation mechanism" philosophy, enables event logging, analytics, and potential undoable tool history.

```
Toolbar click
    │
    ├─ dispatcher.execute({ id: 'tool.activate', payload: { toolId: 'draw-building' } })
    │       │
    │       └─ handler → toolRegistry.activate('draw-building')
    │
    └─ (direct toolRegistry.activate() is deprecated — use command instead)

Keyboard shortcut (1-9)
    │
    └─ ShortcutRegistry → dispatcher.execute({ id: 'tool.activate', payload: { toolId } })
            │
            └─ handler → toolRegistry.activate(toolId)

Command palette
    │
    └─ dispatcher.execute({ id: 'tool.activate', payload: { toolId: 'draw-room' } })
            │
            └─ handler → toolRegistry.activate('draw-room')

Programmatic (auto-switch after placement)
    │
    └─ PreviewManager.confirm() → dispatcher.execute({ id: commandId, payload })
            │
            └─ tool stays active or switches to select (tool decides in onDeactivate)

Space+Pan override
    │
    └─ InteractionController → toolRegistry.override('pan')
        (Space is a momentary input override, not a command — this is the only exception)
```

### The `tool.activate` Command

```typescript
// Registered in command registry as:
{
  id: 'tool.activate',
  handler: (ctx, payload: { toolId: string }) => {
    ctx.services.toolRegistry.activate(payload.toolId, makeToolContext(ctx.services))
  }
}
```

This command is the single entry point for all intentional tool switches. The `Space+Pan` override bypasses it by necessity (it is an input-layer override, not an intentional tool switch — the editor should never remember that "Pan was briefly active").

### Toolbar Sync

The `StudioToolbar` currently calls `toolRegistry.activate(id)` directly. In M3.4.3 it will call `dispatcher.execute({ id: 'tool.activate', payload: { toolId } })` instead. The `InteractionController` reads `toolRegistry.activeToolId` (via React state), not Zustand.

### Tool Activation Sources — Summary

| Source | Mechanism | Goes Through Command? | Notes |
|---|---|---|---|
| Toolbar | `dispatcher.execute(tool.activate)` | Yes | Refactored from direct registry call |
| Keyboard shortcut | `dispatcher.execute(tool.activate)` | Yes | ShortcutRegistry maps key → command |
| Command palette | `dispatcher.execute(tool.activate)` | Yes | Same as toolbar |
| Programmatic (post-placement) | `toolRegistry.activate()` directly | No | Tool-internal; acceptable |
| Space+Pan | `toolRegistry.override()` directly | No | Input override, not an intentional switch |

## 11. Workspace Context Validation

When the editing context changes (Campus → Building → Floor), the active tool may no longer be valid for the new context. `ToolRegistry` enforces this through a validation step.

### Context Change Flow

```
editingContext.setMode('floor')
    │
    ├─ 1. Update editing mode to 'floor'
    ├─ 2. Emit context.changed { previousMode: 'campus', currentMode: 'floor' }
    │
    └─ ToolRegistry.onContextChanged(services)
            │
            ├─ Read activeTool.validIn (if set)
            │
            ├─ If activeTool.validIn is undefined → tool is valid everywhere → no-op
            │
            ├─ If 'floor' is in activeTool.validIn → tool is valid → no-op
            │
            └─ If 'floor' is NOT in activeTool.validIn
                    │
                    ├─ Deactivate current tool
                    └─ Activate default tool for 'floor' mode
```

### Default Tools Per Context

| Editing Mode | Default Tool | Reason |
|---|---|---|
| `campus` | `select` | Most common campus interaction |
| `building` | `select` | Most common building interaction |
| `floor` | `select` | Most common floor interaction |

### Tool Validation Rules

| Editing Mode | Valid Tools |
|---|---|
| `campus` | `select`, `pan`, `draw-road`, `draw-building` |
| `building` | `select`, `pan`, `draw-building` |
| `floor` | `select`, `pan`, `draw-room`, `draw-hallway`, `place-entrance`, `place-staircase`, `place-elevator`, `place-panorama`, `place-qr` |

### Implementation

```typescript
class ToolRegistry extends BaseEditorService {
  // ... existing methods ...

  /** Called when editing context changes. Validates and possibly switches active tool. */
  onContextChanged(newMode: EditorMode, ctx: ToolContext): void {
    const active = this.activeTool
    if (!active) return

    const validIn = active.validIn
    if (!validIn) return // tool valid everywhere

    if (!validIn.includes(newMode)) {
      const defaultTool = this.getDefaultToolForMode(newMode)
      this.activate(defaultTool, ctx)
    }
  }

  private getDefaultToolForMode(mode: EditorMode): string {
    // Always returns 'select' as the safe default
    return 'select'
  }
}
```

## 13. Tool Events

| Event | Emitted By | Payload | Description |
|---|---|---|---|
| `tool.changed` | ToolRegistry | `{ toolId, kind, previousToolId }` | Active tool changed |
| `tool.overridden` | ToolRegistry | `{ toolId, previousToolId }` | Temporary override activated |
| `tool.restored` | ToolRegistry | `{ toolId, restoredFrom }` | Override ended, previous tool restored |
| `preview.changed` | Active Tool | `{ toolId, payload, previewGeometry }` | Preview state updated |
| `preview.confirmed` | Active Tool | `{ toolId, commandId }` | Preview confirmed, command dispatched |
| `preview.cancelled` | Active Tool | `{ toolId }` | Preview cancelled |
| `tool.cursorChanged` | ToolRegistry | `{ cursor }` | Active tool's cursor changed |

## 14. Tool Invariants

1. **Exactly one primary tool is active at all times.** `ToolRegistry.activeToolId` is never null during normal editor operation.
2. **Tools receive events, not raw map callbacks.** The InteractionController routes all pointer/keyboard input through the Tool interface. No tool behavior is hardcoded in the router.
3. **Selection survives tool changes.** Activation never clears selection. Only explicit user actions (Escape, click empty space) or entity deletion clear it.
4. **Only the active tool may change the cursor.** `InteractionController` reads `activeTool.cursor`. No component calls `canvas.style.cursor = ...` directly.
5. **Module-level mutable state is forbidden.** Tools must scope state to the tool instance and reset it in `onActivate()`.
6. **Every mutation is previewed first.** `isMutating === true` tools must go through the Preview → Confirm → Command pipeline. Non-mutating tools skip Preview.
7. **Tool activation goes through ToolRegistry.** No code calls `onActivate()` directly or sets `activeToolId` bypassing the registry.
8. **The Space+Pan override is the only momentary tool mechanism.** No other tool may temporarily override the active tool.
9. **`PointerManager` never calls `SelectionManager.select()` during pointer move.** The `InteractionController` bridges pointer events to selection. `PointerManager` tracks hover, not selection.

### Future Tool Interface Direction

The current `Tool` interface defines one method per input type (`onPointerDown`, `onKeyDown`, etc.). As the number of input types grows (wheel, context menu, touch, stylus, selection changed, document changed, viewport changed), consider evolving to a unified dispatch:

```typescript
// Future direction — not adopted in M3.4.3
tool.handle(event: ToolEvent): void
```

Where `ToolEvent` is a discriminated union:

```typescript
type ToolEvent =
  | { kind: 'pointerDown'; x, y, lng, lat, ... }
  | { kind: 'keyDown'; key, shiftKey, ... }
  | { kind: 'confirm'; ... }
  | { kind: 'cancel'; ... }
```

This keeps the interface stable as new input types are added. The current per-method interface is preferred for M3.4.3 because it is more discoverable for tool authors.
