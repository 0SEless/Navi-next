# M3.4.4 — Context Panel Specification

**Status:** Accepted
**Date:** 2026-07-12
**Dependencies:** M3.4.1 (Editor Interaction), M3.4.2 (Selection System), M3.4.3 (Tool System), ADR 0016 (Active Tool Lifecycle)

---

## 1. Purpose

The Context Panel is the editor's primary communication channel back to the user. It resolves from the aggregate of selection state, active tool, preview state, workflow state, and document state to display the appropriate content — entity editors, tool information, workflow orchestration, or multi-entity editing.

M3.4.4 defines the Context Panel architecture: the `ContextResolver` that maps editor context to panel content, the entity editor registry, the confirm/cancel integration with `PreviewManager`, the Multi Editor, the Tool Info panel, and the Validation Issue Banner.

---

## 2. Context Panel Principles

1. **The Context Panel never owns data.** It resolves from editor context and renders editors. It never stores or manages state.
2. **Content is driven by context, not by routing.** The `ContextResolver` maps the aggregate of selection, tool, preview, and workflow state to the correct content. No component navigates to "pages" within the panel.
3. **Every entity type has a registered editor.** Adding a new entity type means registering an editor component — not modifying the Context Panel.
4. **All edits are immediate.** Field change → `entity.update` command → `CampusDocument` mutation → re-render. No save button within entity editors.
5. **Preview confirmation is driven by `PreviewManager`, not by the active tool.** The ConfirmBar reads `PreviewManager.current` and displays confirm/cancel actions accordingly.
6. **Preview is an overlay state, not a content replacement.** When Preview is active, the existing entity editor remains visible and the ConfirmBar overlays below it. Selection always wins over Preview — clicking an entity while drawing shows its properties.
7. **ToolInfo is supplemental, not primary content.** It renders as a help banner within the Content Area, not as a replacement for entity editors.
8. **The Context Panel is resizable.** The panel width is user-adjustable within min/max bounds.
9. **Validation issues are displayed as banners on the entity editor, not as panel replacements.** The current context never disappears when a validation issue is selected.

## 3. Context Panel Architecture

```
Editor State
    │
    ├─ SelectionManager  → selection.snapshot
    ├─ ToolRegistry      → activeToolId, activeTool
    ├─ PreviewManager    → preview.current
    ├─ WorkflowService   → workflow state
    ├─ ValidationService → validation issues
    └─ CampusDocument    → entity data
            │
            ▼
    ContextResolver.resolve(editorContext)
            │
            ▼
    PanelRegistry.lookup(resolvedKind)
            │
            ▼
    ┌─────────────────────────────────────────────────┐
    │              Context Panel                       │
    │                                                   │
    │  ┌─────────────────────────────────────────────┐  │
    │  │           Content Area                       │  │
    │  │                                               │  │
    │  │  [EntityEditor / MultiEditor]                │  │
    │  │                                               │  │
    │  │  ┌─ Issue Banner (conditional) ───────────┐  │  │
    │  │  │  Validation issue description           │  │  │
    │  │  │  [Fix] [Dismiss]                       │  │  │
    │  │  └────────────────────────────────────────┘  │  │
    │  │                                               │  │
    │  │  ┌─ Tool Help (conditional) ──────────────┐  │  │
    │  │  │  Click to place route points. Min 2.   │  │  │
    │  │  └────────────────────────────────────────┘  │  │
    │  │                                               │  │
    │  │  ┌─ Metadata Form (preview only) ────────┐  │  │
    │  │  │  Route Name: [___] Type: [___]        │  │  │
    │  │  └────────────────────────────────────────┘  │  │
    │  │                                               │  │
    │  └─────────────────────────────────────────────┘  │
    │                                                   │
    │  ┌─────────────────────────────────────────────┐  │
    │  │  ConfirmBar (conditional)                    │  │
    │  │  [Undo] [Point: 4/3] [Confirm] [Cancel]     │  │
    │  │  (actions only — no forms)                   │  │
    │  └─────────────────────────────────────────────┘  │
    └─────────────────────────────────────────────────┘
```

### Layers (bottom to top)

| Layer | Content | Conditional? |
|---|---|---|
| **Entity Editor** | Primary content (entity form, multi-editor, workflow card, or workspace home) | No — always one is shown |
| **Issue Banner** | Validation issue description + [Fix] [Dismiss] | Yes — shown when validation issue selected |
| **Tool Help** | Contextual instructions for the active tool | Yes — shown when tool active |
| **Metadata Form** | Post-drawing form fields (route name, type, etc.) | Yes — shown only during Preview |
| **ConfirmBar** | Confirm/cancel actions | Yes — shown when `PreviewManager.isActive === true` |

### Context Panel Sections

The Context Panel has two structural sections:

1. **Content Area** — the primary content, resolved by `ContextResolver` and rendered through `PanelRegistry`. Contains Entity Editor + optional overlays (Issue Banner, Tool Help, Metadata Form).
2. **ConfirmBar** — a conditional footer bar, shown when `PreviewManager.isActive === true`. Contains only action controls (Undo, Confirm, Cancel). Never contains forms.

## 4. PanelRegistry

`PanelRegistry` is a service that stores all panel/editor registrations. It is separate from `ContextResolver` so that registration and resolution are independent concerns.

```typescript
class PanelRegistry extends BaseEditorService {
  readonly id = 'panelRegistry'
  readonly dependencies: string[] = []

  /** Register an editor component for an entity type. */
  registerEditor(entityType: string, editor: EntityEditorComponent): void

  /** Register a panel for a context kind. */
  registerPanel(kind: PanelKind, panel: PanelComponent): void

  /** Get the registered editor for an entity type. */
  getEditor(entityType: string): EntityEditorComponent | undefined

  /** Get the registered panel for a context kind. */
  getPanel(kind: PanelKind): PanelComponent | undefined

  /** Get all registered entity types. */
  get registeredEntityTypes(): string[]
}
```

`EntityEditorComponent` and `PanelComponent` are React component types. They are stored as `React.ComponentType<EditorProps>` — the `PanelRegistry` is aware of UI because its purpose is UI registration. Framework-independence lives at the resolver layer.

## 5. ContextResolver

The `ContextResolver` maps editor state to a `PanelDescriptor`. It is framework-independent — it does not import or return React components.

```typescript
class ContextResolver extends BaseEditorService {
  readonly id = 'contextResolver'
  readonly dependencies = ['selection', 'toolRegistry', 'preview', 'workflow', 'validation', 'panelRegistry']

  /** Resolve the current editor context into a panel descriptor. */
  resolve(context: EditorContext): ContextResolution
}

interface ContextResolution {
  /** The primary panel kind for the content area. */
  primaryKind: PanelKind
  primaryProps: Record<string, unknown>

  /** Whether a Tool Help banner should be shown. */
  showToolHelp: boolean

  /** Validation issue banner (if any). */
  validationBanner: ValidationIssue | null

  /** Whether a metadata form should be shown (during Preview). */
  showMetadataForm: boolean

  /** Whether the ConfirmBar should be shown. */
  showConfirmBar: boolean
}

type PanelKind =
  | 'workflowCard'
  | 'entityEditor'
  | 'multiEditor'
  | 'workspaceHome'
  | 'publishProgress'
```

### Resolution Priority

```
Input: editorContext { selection, tool, preview, validation, publishing, document }

Output: ContextResolution

1. No document loaded        → workspaceHome, no extras
2. Publishing active         → publishProgress, no extras
3. Validation issue + entity → entityEditor + validationBanner
4. Single selection          → entityEditor + toolHelp (if tool active)
5. Multi-selection           → multiEditor + toolHelp (if tool active)
6. Tool active, no selection → workflowCard + toolHelp
7. Nothing active            → workflowCard
8. Preview always            → existing primary + metadataForm + confirmBar
```

Note: Preview does not change the primary content. If a building is selected and the user is drawing a road, the panel shows `buildingProperties + metadataForm + confirmBar`. Selection wins over Preview for primary content.

### Implementation

```typescript
class ContextResolver extends BaseEditorService {
  resolve(ctx: EditorContext): ContextResolution {
    // Document state
    if (!ctx.document) {
      return { primaryKind: 'workspaceHome', primaryProps: {}, showToolHelp: false, validationBanner: null, showMetadataForm: false, showConfirmBar: false }
    }

    if (ctx.publishing) {
      return { primaryKind: 'publishProgress', primaryProps: {}, showToolHelp: false, validationBanner: null, showMetadataForm: false, showConfirmBar: false }
    }

    // Determine primary content
    let primaryKind: PanelKind
    let primaryProps: Record<string, unknown>

    if (ctx.validationIssue) {
      primaryKind = 'entityEditor'
      primaryProps = { entity: ctx.validationIssue.entity }
    } else if (ctx.selection && ctx.selection.length >= 1) {
      primaryKind = ctx.selection.length > 1 ? 'multiEditor' : 'entityEditor'
      primaryProps = { entities: ctx.selection }
    } else {
      primaryKind = 'workflowCard'
      primaryProps = {}
    }

    // Determine extras
    const showToolHelp = !!ctx.toolActive
    const validationBanner = ctx.validationIssue ?? null
    const showMetadataForm = ctx.preview?.needsMetadata ?? false
    const showConfirmBar = ctx.preview?.isActive ?? false

    return { primaryKind, primaryProps, showToolHelp, validationBanner, showMetadataForm, showConfirmBar }
  }
}
```

The `ContextPanel` component takes the `ContextResolution`, looks up components in `PanelRegistry`, and renders:

```typescript
// ContextPanel renders:
<div>
  <ContentArea>
    <PanelRegistry.getPanel(resolution.primaryKind) {...resolution.primaryProps} />
    {resolution.validationBanner && <IssueBanner issue={...} />}
    {resolution.showToolHelp && <ToolHelp tool={...} />}
    {resolution.showMetadataForm && <MetadataForm />}
  </ContentArea>
  {resolution.showConfirmBar && <ConfirmBar />}
</div>
```

## 6. Panel Content Types

### WorkflowCard

Shown when nothing is selected and no tool is active. Replaces the current behavior of showing the workflow card in the PropertiesPanel.

**State:** 4-step state machine: Validate → Compile → Save → Publish
**Consumers:** `WorkflowService`, `ValidationService`
**Interactions:** Click step to expand, click action button to trigger step

Already implemented at `packages/editor/src/panels/workflow/workflow-card.tsx`. No architectural changes needed.

---

### EntityEditor

Shown when a single entity is selected. Each entity type registers its own editor component in the `ContextResolver`.

**Existing Editors** (from current PropertiesPanel):

| Entity Type | Editor Component | Fields |
|---|---|---|
| `building` | BuildingProperties | name, code, category, description, color, baseElevation, height |
| `floor` | FloorProperties | label, elevation |
| `room` | RoomProperties | name, number, category, capacity |
| `hallway` | HallwayProperties | name, width, color |
| `road` | RoadProperties | name, width, surface, type |
| `entrance` | EntranceProperties | label, type, hasQR, hasPanorama |
| `staircase` | StaircaseProperties | name, fromLevel, toLevel, type |
| `elevator` | ElevatorProperties | name, fromLevel, toLevel |
| `panorama` | PanoramaProperties | label, heading, imageAssetId |
| `qr` | QRProperties | label, code |

**All edits are immediate.** Each field change dispatches `entity.update` → `CampusDocument` mutation → re-render. No save button.

These editors already exist at `packages/editor/src/panels/properties/*-props.tsx`. They are migrated from the old `switch`-based `PropertiesPanel` to the registry-based `ContextResolver`.

### MultiEditor

Shown when 2+ entities are selected. Displays only properties that exist on all selected entities.

```typescript
interface MultiEditorProps {
  entities: { entityType: string; entity: EntityData }[]
}

// Resolution logic:
// 1. If all entities share the same type → show shared properties (name, label, etc.)
// 2. If entities have different types → show only common metadata (name, position)
// 3. Any field change dispatches entity.update for ALL selected entities
```

**MultiEditor Rules:**

- All entities must be of the same type for type-specific properties to appear.
- Mixed-type selections show only `name`/`label` and `position` (properties that all entities share).
- Field values shown when all selected entities share the same value.
- Field shows `— (mixed)` when values differ.
- Editing a field dispatches `entity.update` for each selected entity individually.

Not yet implemented.

### ConfirmBar (Context Panel Footer)

The ConfirmBar moves from the canvas bottom overlay into the Context Panel footer. It contains **actions only** — no forms, no metadata inputs.

```typescript
interface ConfirmBarProps {
  preview: PreviewState
  onUndo: () => void
  onConfirm: () => void
  onCancel: () => void
}
```

**Content (actions only):**

| Element | Description |
|---|---|
| Tool label + icon | e.g., "Create Building" |
| Point count | e.g., "Points: 4/3" (current / min) |
| Undo button | Removes last vertex/point |
| Confirm button | Dispatches the command (disabled until min points met) |
| Cancel button | Clears preview state |

**When is ConfirmBar visible?**

```
PreviewManager.isActive === true
  AND activeToolId matches the tool that published the preview
```

**Position:**

The ConfirmBar renders at the bottom of the Context Panel, above the resize handle. It replaces the current floating canvas-bottom overlay position.

**Metadata Form:**

When Preview is active and the command requires user-provided metadata (e.g., route name, type, width), a `MetadataForm` is shown in the Content Area above the ConfirmBar. It is conceptually separate — the ConfirmBar remains action-only.

```
Content Area
    │
    ├─ Entity Editor (existing)
    ├─ Metadata Form    ← "Route Name: [___] Type: [___]"
    └─ ConfirmBar      ← [Undo] [Confirm] [Cancel]
```

**Transition Period:**

During M3.4.4, ConfirmBar is duplicated in both places (canvas bottom + Context Panel footer). The canvas-bottom version is removed in M3.4.5 once the Context Panel version is validated.

Validation issues are displayed as a banner within the Content Area, overlaying the entity editor. The current context never disappears.

## 7. ConfirmBar Architecture

### Current State (Canvas-Bottom Overlay)

- `ConfirmBar.tsx` renders as an absolute-positioned overlay at the bottom of the canvas.
- Reads from `useStudioStore` (Zustand), not from `PreviewManager`.
- Shows tool label, point count, undo/confirm/cancel.
- Separate `ConfirmOverlay` shows a form dialog for route metadata.

### Target State (Context Panel Footer)

- ConfirmBar renders inside the Context Panel footer, below the content area.
- Contains **actions only** — Undo, Confirm, Cancel. No forms.
- Reads from `PreviewManager.current` (via `useEditor().services.get('preview')`).
- Post-preview metadata forms (route name, type, width) are shown as a `MetadataForm` in the Content Area, above the ConfirmBar — not in the ConfirmBar itself.

```
Content Area
    │
    ├─ EntityEditor (building properties shown while drawing)
    ├─ ToolHelp ("Click to place points. Min 2.")
    ├─ MetadataForm ("Route Name: [___] Type: [___]")
    │
    └─ ConfirmBar
        ├─ [Undo]  [Point: 4/2]  [Confirm]  [Cancel]
```

### Flow (Target)

```
Tool finishes accumulation (Enter / DblClick)
    │
    └─ Tool calls PreviewManager.publish({ toolId, commandId, label, payload, previewGeometry })
            │
            ├─ PreviewManager.isActive = true
            ├─ emit preview.changed
            │
            ├─ ContextResolver resolves primary content normally
            │   (selection wins — entity editor stays visible)
            │       │
            │       ├─ Content Area → EntityEditor (existing selection preserved)
            │       ├─ ToolHelp       → shown (tool is active)
            │       ├─ MetadataForm   → shown (if preview.needsMetadata)
            │       └─ ConfirmBar     → shown (preview.isActive === true)
            │
            ├─ User selects a different entity while drawing
            │       │
            │       ├─ EntityEditor updates to show new entity
            │       ├─ Preview still active (ConfirmBar stays)
            │       ├─ MetadataForm still shown
            │       └─ Canvas still shows preview geometry
            │
            ├─ User clicks Confirm
            │       │
            │       ├─ PreviewManager.confirm(ctx)
            │       │       └─ dispatcher.execute(command)
            │       ├─ emit preview.confirmed
            │       ├─ PreviewManager.isActive = false
            │       └─ ConfirmBar + MetadataForm hidden
            │
            └─ User clicks Cancel
                    │
                    ├─ PreviewManager.cancel()
                    ├─ emit preview.cancelled
                    ├─ PreviewManager.isActive = false
                    ├─ ConfirmBar + MetadataForm hidden
                    └─ Tool resets accumulation state
```

## 7. Resizable Width

The Context Panel supports user-adjustable width.

| Property | Value |
|---|---|
| Default width | 320px |
| Minimum width | 240px |
| Maximum width | 480px |
| Resize handle | Left edge of panel |
| Persistence | Width is stored in `UIStore` (non-persistent, resets on reload) |

The resize handle is a 4px-wide grab area on the left edge of the Context Panel. It shows a `col-resize` cursor on hover. Drag left/right to adjust width.

Current implementation uses a fixed 280px. Changing to flexible resizable width requires:
1. Adding a resize handle component.
2. Replacing `width: 280` with `width: panelWidth` (state variable).
3. Adding mouse drag handling to update `panelWidth`.

## 10. Context Panel Invariants

1. **The Context Panel never owns data.** It renders from editor context. No state is stored in the panel.
2. **All edits are immediate.** Field change dispatches `entity.update` — no save button.
3. **Preview confirmation is owned by `PreviewManager`.** The ConfirmBar reads `PreviewManager.current`. It never reads from the active tool directly.
4. **Entity resolution follows priority order.** The `ContextResolver` applies the resolution priority (Section 4) unconditionally.
5. **Every entity type has at most one registered editor.** Registering a second editor for the same type overwrites the first.
6. **The ConfirmBar is visible only when `PreviewManager.isActive === true`.** No other condition shows it.
7. **Multi-selection editing dispatches one `entity.update` per entity.** Each selected entity receives its own command.

## 11. Non-Goals

The following are excluded from M3.4.4:

- Validation Issue Viewer with interactive issue selection — the infrastructure for selecting validation issues is deferred; the `IssueViewer` component structure is defined but inactive.
- Property search within editors — M4.
- Collapsible editor sections — M4.
- Keyboard-navigable property fields — M3.4.5 (Input System).
- Inline property validation (field-level error indicators) — M3.5.
