# M3.4.1 — Editor Interaction & Workspace Specification

**Status:** Accepted
**Date:** 2026-07-12
**Dependencies:** M3.3.4 (Publish Pipeline), ADR 0015 (Service Boundaries)

---

## Purpose

This document defines **how a human interacts with NAVI Studio**. It covers workspace layout, canvas interaction, tool philosophy, selection model, the context panel, keyboard architecture, context menus, and the status bar.

It is the interaction-level companion to the service architecture established in M3.2–M3.3.4. Where those milestones defined the **backend infrastructure**, this specification defines the **frontend interaction model** built on top of it.

This document specifies **interaction behavior only**. It intentionally does not prescribe React components, hook implementations, state management details, or rendering techniques. Those belong to implementation documents.

---

## Editor Interaction Principles

1. **Canvas renders. Tools interact.** The canvas owns display and hit-testing. Tools own behavior. Neither crosses into the other's responsibility.
2. **Selection is the single source of truth for entity targeting.** All UI components (Canvas, Explorer, Context Panel, Status Bar, Workflow) consume from `SelectionManager`. Nothing else owns selection.
3. **Preview before commit.** Every editing operation that mutates `CampusDocument` enters a preview state first. A Confirm Panel must be explicitly confirmed or cancelled before a Command is dispatched.
4. **Every modification becomes a Command.** No UI component, tool, or service may mutate `CampusDocument` directly. All changes flow through `CommandDispatcher`.
5. **Context drives the UI, not pages.** NAVI Studio is a single-workspace editor. Users navigate by changing editing context—not by navigating to different editor pages or routes. The workspace layout is persistent; only the editing context changes.
6. **Input devices are interchangeable.** The interaction model is defined in terms of Primary Action, Secondary Action, Confirm, Cancel, and Modifier—not mouse clicks or touch events. This future-proofs the model for touch, pen, and alternative input.
7. **The Context Panel always reflects the current editor context.** It is not merely a Properties Panel. It resolves from the aggregate of active tool, selection state, document state, and workflow state.
8. **The Status Bar reflects editor state but never controls it.** It is a read-only display of context path, selection, cursor, workflow, validation status, and active tool. It does not contain buttons or interactive controls.

## 1. Workspace Layout

### Principle

NAVI Studio is a **single-workspace editor**. Users navigate by changing editing context—not by navigating to different editor pages. The workspace layout is persistent. Only the editing context changes.

### Three Orthogonal Contexts

The editing context is the combination of three independent dimensions:

| Context | Owned By | Examples | Determines |
|---|---|---|---|
| **Workspace Context** | Explorer / ViewportManager | Campus, Building, Floor | Which entities are visible, which tools are available |
| **Selection Context** | SelectionManager | None, single, multiple | Which entities are targeted by commands |
| **Tool Context** | ToolRegistry | Select, Draw Room, Vertex Edit | How input is interpreted, what overlays appear |

These are continuously combined. A user might be working on **Floor 2** (Workspace Context), editing **Room 204** (Selection Context), using the **Vertex Edit** tool (Tool Context). Each is independent.

### Layout

```
+----------------------------------------------------+
| Toolbar                                            |
+----------+----------------------------+------------+
| Explorer |         Canvas             |  Context   |
|  (tree)  |  (MapLibre + overlays)     |   Panel    |
|  search  |                            |            |
|          |                            |            |
|  Campus  |  DrawingOverlay            |  Workflow  |
|  ├─ Bldg |  ConfirmBar                |  │         |
|  │  └─Fl |  SelectionOverlay          |  Editor    |
|  ├─ Road |  PreviewOverlay            |  │         |
|  └─ Asst |  ViewportController        |  Multi     |
|          |  Status Bar                |  │         |
|          |                            |  ToolInfo  |
+----------+----------------------------+------------+
```

- **Single route:** `/studio/[id]/edit` for all editing. No dedicated Floor Editor route.
- **Toolbar:** Full-width top bar. Shows mode-based tool groups, undo/redo, and workspace-level controls.
- **Explorer (left, 220px):** Entity tree with search, inline rename, right-click context menu. Drives editing context (selecting a building in Explorer focuses the editor on that building). Floor selection happens by drilling into the tree, not via route changes.
- **Canvas (center, flex):** MapLibre GL JS with overlay components. Owns display and hit-testing only.
- **Context Panel (right, flexible width):** Content depends on current editor context (see Section 5). Default width accommodates entity editors.
- **Status Bar (bottom, full width):** Read-only display (see Section 9).

### Editing Session Lifecycle

An editing session begins when a campus document is opened and ends when it is closed.

**Open → Restore → Ready → Close**

1. **Open:** Load `CampusDocument` from storage. Create editor services (dispatcher, history, selection, tools, workflow, validation, publish).
2. **Restore:** Restore viewport position, active floor, selection, and active tool from persisted state (if any).
3. **Ready:** Editor is fully interactive. Restore Explorer expansion state, selected floor, active tool, viewport position, and panel sizes from persisted session state.
4. **Close:** If unsaved changes exist, prompt user. Autosave pending work. Dispose services and release resources.

The session lifecycle is managed by the workspace shell (`EditorShell`), not by individual panels or tools.

## 2. Canvas Interaction

### Ownership

The active tool owns interaction behavior. The canvas only renders and forwards input:

```
Active Tool → InteractionController → Canvas
```

`InteractionController` routes all pointer and keyboard events to the active tool. The canvas never decides behavior. Input controllers normalize device-specific events (mouse, touch, pen) into editor actions before forwarding them to the active tool.

### Gesture Table

| Action | Behavior |
|---|---|
| **Primary Action** (click, tap) | Hit-test in priority order. If hit, select. If miss, clear selection. If drawing, add point. |
| **Secondary Action** (right-click, long-press) | Open context menu for the entity under the cursor. |
| **Confirm** (double-click, Enter) | Finalize active drawing. If not drawing, center + zoom on entity under cursor. |
| **Cancel** (Escape) | If Confirm Panel active → cancel. If drawing → cancel drawing. If nothing pending → clear selection. |
| **Drag** | If on entity and select tool → move. If on empty space → marquee select. If drawing → place geometry (rectangle). If vertex edit → move vertex. |
| **Modifier held** | Interpreted by active tool (e.g., Shift → constrain, Ctrl → multi-select). |
| **Hover** | Show tooltip with entity name + type. Change cursor to indicate interactivity. |
| **Scroll** | Zoom (MapLibre default). |

### Hit-Test Priority (descending)

1. Vertex handle
2. Selection/transform handle
3. Node
4. Entrance
5. Road
6. Room
7. Building
8. Campus boundary
9. Background (clear selection)

### Immediate vs Confirmed Editing

NAVI Studio supports two editing families:

| Type | Examples | Commit Model |
|---|---|---|
| **Immediate Operations** | Rename, change category, edit description, toggle checkbox | Field change → `entity.update` command → document updated immediately. No Confirm Panel. |
| **Preview Operations** | Draw, move, rotate, delete many, merge, split | Enter preview → place/modify geometry → Confirm Panel → Command. Document is not updated until confirmed. |

Immediate operations are used for metadata edits where each change is independently meaningful. Preview operations are used for spatial changes where the user needs to see the result before committing.

### Drawing Workflow

```
Activate Tool → Preview State → Place Points → Confirm Panel → Confirm/Cancel → Command → CampusDocument
```

- Activating a creation tool enters preview state (crosshair cursor, dragPan disabled).
- Points rendered on `s-drawing` source via `DrawingOverlay`.
- `ConfirmBar` appears at canvas bottom with Confirm / Cancel buttons.
- The Confirm Panel does **not** own the preview geometry. It only asks "Confirm?" or "Cancel?". The active tool owns the temporary geometry.
- Double-click or press Confirm → finalize → dispatches command.
- Escape or press Cancel → discard → no command dispatched.
- Only tools capable of mutating CampusDocument may enter Preview state.

### UX Invariants

- The active tool owns interaction behavior; the canvas only renders and forwards input.
- Every editing operation that changes the document enters a Preview state first.
- The Confirm Panel is the standard mechanism for committing or cancelling document changes.
- Every document modification is committed through a Command via CommandDispatcher.
- Selection has a single source of truth and is reflected consistently across Canvas, Explorer, Context Panel, and Status Bar.

### Selection Highlighting

Canvas selection must work bidirectionally:
- Canvas click → `SelectionManager.select()` → canvas highlights + inspector shows entity
- Explorer click → `SelectionManager.select()` → canvas highlights + inspector shows entity

Selected entities get `feature-state` on MapLibre layers. Hovered entities get a subtle glow. Rendering priority: **Editing > Selection > Hover > Normal**.

## 3. Tool Philosophy

### Principles

- **Tools are behavior modules, not application modes.** Activating a tool changes how input is interpreted, not what the application is doing.
- **Only one primary tool may be active at a time.** The active tool owns interaction. Everything else is secondary.
- **Tools may own temporary interaction state** (preview polygon, cursor position, temporary handles) but **never document state**. `CampusDocument` remains the sole source of truth.
- **Only mutating tools enter Preview and display the Confirm Panel.** Navigation and Selection tools never do.
- **Only the active tool may change the cursor.** No component sets `canvas.style.cursor` directly.
- **Tool activation goes through CommandDispatcher.** Toolbar clicks, keyboard shortcuts (`1`–`9`), command palettes, macros, and tutorials all activate tools by dispatching a `tool.activate` command. This keeps all activation paths consistent.

### Standard Tool Lifecycle

```
onActivate()
    ↓
Interaction (pointer/keyboard events routed to tool)
    ↓
Preview (optional — mutating tools only)
    ↓
Confirm / Cancel (via Confirm Panel)
    ↓
Dispatch Command → CommandDispatcher → CampusDocument
    ↓
onDeactivate()
```

### Tool Categories

| Category | Purpose | Tools | Uses Confirm Panel? |
|---|---|---|---|
| **Navigation** | Move around the workspace | Pan, Zoom | No |
| **Selection** | Select and inspect entities | Select, Lasso (future) | No |
| **Creation** | Create new entities | Draw Building, Draw Room, Draw Road, Place Entrance, Place Staircase, Place Elevator, Place Panorama, Place QR | Yes |
| **Modification** | Modify existing entities | Vertex Edit, Move (future), Rotate (future) | Yes |
| **Analysis** | Measure, validate, inspect | Measure (future) | No |
| **Utility** | Calibration, debugging | Calibrate | No |

### Persistent vs Momentary Tools

| Type | Examples | Behavior |
|---|---|---|
| **Persistent** | Select, Draw Building, Draw Room, Vertex | Stay active until explicitly switched |
| **Momentary** | Pan (Space hold) | Active only while key/button held; previous tool resumes on release |

Space bar implements a **temporary tool override**: holding Space activates Pan regardless of the current tool. Releasing Space returns to the previous tool without switching or deactivating it.

### Mode-Based Tool Filtering

The toolbar shows only tools relevant to the current editing mode, which is determined by the Explorer context:

| Context | Available Tools |
|---|---|
| Campus | Select, Pan, Draw Road, Draw Building |
| Building (selected) | Select, Pan, Draw Building |
| Floor (selected) | Select, Pan, Draw Room, Draw Hallway, Place Entrance, Place Staircase, Place Elevator |

The mode label in the Status Bar reflects the deepest context level: `Campus > Admin Building > Floor 2`.

### Tool vs Manipulator (Future)

This specification anticipates the M3.5 distinction between Tool (which interaction is active) and Manipulator (how geometry changes). The `VertexEdit` tool will use a `VertexManipulator`; the `Move` tool will use a `TranslationManipulator`. This separation is not implemented in M3.4 but the architecture supports it.

## 4. Selection Model

### ViewportManager Ownership

**ViewportManager owns all camera movement.** No component calls `map.flyTo()`, `map.easeTo()`, or `map.fitBounds()` directly. All camera operations go through `ViewportManager`, which decides whether to animate, how to animate, and whether to interrupt an existing animation.

The ViewportManager listens to `selection.changed` and decides whether to fly to the selected entity based on origin:
- Canvas origin → no flyTo (user is already looking there)
- Explorer origin → no flyTo (user is already looking there)
- Keyboard origin → flyTo if entity is off-screen
- Programmatic → depends on caller

`SelectionManager` does not own camera behavior. It emits changed events. `ViewportManager` decides how to react.

### Four Interaction States

| State | Purpose | Owned By | Visual |
|---|---|---|---|
| **Hover** | What's under the cursor | `SelectionManager` | Subtle highlight, tooltip |
| **Selection** | Active entity set | `SelectionManager` | Cyan outline/glow |
| **Focus** | Current viewport/navigation context | `ViewportManager` | Explorer expansion, breadcrumb |
| **Editing** | Actively modified entity | Active Tool | Handles, transform controls |

These states are orthogonal. An entity can be hovered without being selected, selected without being edited, and the viewport can focus on a building while editing a room inside it.

### Single Source of Truth

```
Explorer ─┐
Canvas ───┼──→ SelectionManager → Canvas, Context Panel, Explorer, Status Bar
Keyboard ─┘                                   (all read from same source)
```

`SelectionManager` owns selection state. Every UI component is a consumer. Nothing else owns selection. SelectionManager emits three event types: `selection.changed` (selection set modified), `selection.cleared` (selection emptied), and `selection.focusRequested` (viewport should focus a specific entity).

### Selection Origins

Each selection carries its origin for behavior gating. `SelectionManager` emits `selection.changed` with the origin. `ViewportManager` consumes this event and decides camera behavior (see ViewportManager Ownership above):

| Origin | ViewportManager Behavior |
|---|---|
| `canvas` | No camera movement (user is already looking there) |
| `explorer` | No camera movement (user is already looking there) |
| `keyboard` | flyTo if entity is off-screen |
| `programmatic` | Depends on caller |

### Persistence

Selection persists until explicitly cleared. These are the only actions that clear selection:

- Primary Action on empty canvas space
- Escape (when no Confirm Panel or drawing is active)
- Entity deletion
- Opening another document
- Explicit "Clear Selection" command

**Selection survives tool changes.** Switching from Select to Draw Room does not clear selection.

### Multi-Select

| Action | Behavior |
|---|---|
| `Ctrl+click` / `Cmd+click` | Toggle entity into/out of selection set |
| `Shift+click` (Explorer) | Range select |
| `Ctrl+A` | Select all in current context |
| Drag on empty space | Marquee select (M3.5) |

Selection set shown in Status Bar: `Selected: 3`.

### Commands Default to Selection

Every command operates on the current selection unless the active tool explicitly overrides the target:

- Delete → deletes selected entities
- Duplicate → duplicates selected entities
- Move → moves selected entities

## 5. Context Panel

### Principle

The Context Panel replaces the traditional "Properties Panel." Its content depends on the current editor context—the aggregate of active tool, selection state, document state, and workflow state. It is not merely coupled to selection.

### Resolver Architecture

```
Editor Context
    │
ContextResolver.resolve()
    │
    ▼
[WorkflowCard | EntityEditor | MultiEditor | ToolInfo | Welcome | IssueViewer | PublishProgress]
```

The `ContextResolver` takes the current editor context (active tool, selection set, workflow state, validation state) and returns which panel content to render. This is registry-driven: adding a new entity type means registering an editor component, not modifying the Context Panel.

### Panel Contents by Context

| Editor Context | Panel Content |
|---|---|
| No document loaded | **Workspace Overview** — campus info, last save, publish status, validation summary, recent actions |
| Nothing selected, no tool active | **Workflow Card** — 4-step state machine (Validate → Compile → Save → Publish) |
| Nothing selected, tool active | **Tool Info** — tool instructions, current vertex count, active constraints |
| Single entity selected | **Entity Editor** — type-specific form (Building Editor, Room Editor, etc.) |
| Multiple entities selected (same type) | **Multi Editor** — editable intersection of common properties |
| Multiple entities selected (different types) | **Multi Editor** — shared metadata only (name, position) |
| Validation issue clicked | **Entity Editor + Issue Banner** — entity form with validation overlay |
| Publishing | **Workflow Card** (expanded Publish section) |

### Entity Editors

- Each entity type has its own editor component registered in an editor registry.
- All edits are immediate (no save button). Field change → `entity.update` command → `CampusDocument` → `document.changed` → Validation → Autosave → Re-render.
- Read-only fields shown as plain text (computed/derived values).
- Validation feedback shown inline per field.

### Multi Editor

When multiple entities are selected, the Multi Editor shows only properties that can be edited on all of them simultaneously:

```
3 Buildings selected
    Name        ❌ (differs)
    Height      ✓ (editable)
    Category    ✓ (editable)
    Color       ✓ (editable)
```

### Validation Issue Banner

When a validation issue is selected, the Context Panel shows the entity editor with an overlay banner at the top:

```
⚠ Validation Error
Polygon is self-intersecting.
Validator: polygon-self-intersection
Suggested fix: Move vertex #4.
```

The entity editor remains visible underneath. The Context Panel does not switch to a different view.

## 6. Workflow Panel Behavior

The Workflow Card lives within the Context Panel and acts as the editor's orchestration shell. It was built and refined through M3.3.x and remains largely as-is.

### Steps

1. **Validate** — runs validation engine, shows error count
2. **Compile** — generates navigation artifacts
3. **Save** — persists to storage via WorkflowService
4. **Publish** — publishes via PublishService

### Visual Elements

- Progress bar (4px, animated fill)
- Step rows with status indicator (colored dot) and action button
- Dirty badge ("Unsaved changes")
- Next action hint (italic text)
- Steps lock when preconditions aren't met (e.g., cannot save with validation errors)

### Publish Progress

Publish progress is shown as an **expanded Publish section within the Workflow Card**, not as a separate panel replacing the Context Panel. The user retains access to other workflow steps and contextual information.

### Status Bar Integration

Workflow state is mirrored in the Status Bar: dirty/saving/saved/autosaved, validation error/warning count, publish status.

## 7. Keyboard Shortcuts

### Principle

**Keyboard shortcuts are an input mechanism, not a behavior mechanism.** The `ShortcutRegistry` translates keys into command IDs and dispatches them through `CommandDispatcher`. It never executes business logic directly.

Keyboard → ShortcutRegistry → CommandDispatcher → Services

### Context Priority

Shortcuts resolve against a context hierarchy. The highest-priority active context wins:

1. **Text Input Context** — when editing a text field, keystrokes go to the field (not the editor)
2. **Tool Context** — active tool's key bindings take priority
3. **Editor Context** — editor-level shortcuts
4. **Application Context** — global shortcuts

### Reserved Shortcuts

| Shortcut | Command ID | Scope |
|---|---|---|
| `Ctrl+Z` / `Cmd+Z` | `history.undo` | Global |
| `Ctrl+Shift+Z` / `Cmd+Shift+Z` | `history.redo` | Global |
| `Ctrl+S` / `Cmd+S` | `workflow.save` | Global |
| `Ctrl+A` / `Cmd+A` | `selection.selectAll` | Editor |
| `Delete` / `Backspace` | `entity.delete` | Editor |
| `Escape` | (see Cancel priority) | Global |
| `Enter` | (Confirm Panel confirm) | Tool |
| `Space` (hold) | Temporary Pan override | Global |
| `Ctrl` (hold) | Tool-defined modifier | Tool |
| `Shift` (hold) | Tool-defined modifier | Tool |
| `Ctrl+C` / `Cmd+C` | `entity.copy` | Editor |
| `Ctrl+V` / `Cmd+V` | `entity.paste` | Editor |
| `Ctrl+D` / `Cmd+D` | `entity.duplicate` | Editor |
| `1`–`9` | `tool.activate(N)` | Global |
| `Ctrl+F` / `Cmd+F` | `explorer.search` | Editor |
| `?` | `shortcuts.showHelp` | Global |

### Reserved for Future Use

| Shortcut | Notes |
|---|---|
| `Ctrl+P` | Print / Export |
| `Ctrl+N` | New document |
| `Ctrl+O` | Open document |
| `Ctrl+Tab` | Panel navigation |
| `Ctrl+Shift+P` | Command palette (post-M3.4) |
| `Alt` | Menu accelerator |

### Discoverability

Each shortcut in the registry stores full metadata:

```typescript
{
  keys: 'Ctrl+S',
  commandId: 'workflow.save',
  label: 'Save Document',
  group: 'Workflow',
  description: 'Save current CampusDocument'
}
```

This metadata drives:
- The `?` overlay that shows all keyboard shortcuts
- Tooltips on toolbar buttons (toolbar queries the registry)
- Future keyboard shortcut configuration UI (post-M3.4)

### Cancel Priority

Escape resolves in this order:

1. Confirm Panel (if active) → cancel current operation
2. Active drawing (if in Preview) → discard drawing
3. Selection (if anything selected) → clear selection
4. (Nothing to cancel)

### Modifier Keys

Modifier keys (Ctrl, Shift, Alt) are **interpreted by the active tool**, not hardcoded to specific behaviors. For example:
- Rectangle Tool: Shift → perfect square
- Polyline Tool: Shift → 45° angle snapping
- Move Tool: Shift → duplicate while dragging

## 8. Context Menus

### Principle

Context menus expose operations that are valid for the current selection and are **alternative entry points to existing commands**. They never introduce unique functionality unavailable elsewhere.

### Canvas Right-Click

| Context | Menu Items |
|---|---|
| Entity under cursor | Delete, Duplicate, Rename, Zoom To, Copy ID |
| Empty space | Paste, Select All |

### Explorer Right-Click

Already implemented. Extend with:
- Copy
- Duplicate
- Zoom To

### Implementation Rule

All context menu actions dispatch through `CommandDispatcher`. No context menu action may mutate state directly.

## 9. Status Bar

### Principle

The Status Bar reflects editor state but **never controls it**. It is a read-only display with no buttons, inputs, or interactive controls.

### Layout

```
[Campus > Admin Bldg > Floor 2] | [Selected: 3] | [X: 218.3 Y: 91.8] | [Snap: Grid] | [Dirty] | [3 Errors] | Tool: Select
```

### Persistent Elements (always visible)

- **Context breadcrumb:** Current navigation context (Campus > Building > Floor)
- **Selection count:** Number of selected entities
- **Tool name:** Active tool label
- **Workflow state:** Ready / Saved / Dirty / Saving... / Autosaved

### Transient Elements (shown only when relevant)

- **Cursor coordinates:** Shown only when hovering the canvas
- **Snap status:** Shown only when snap is active (M3.5)
- **Validation count:** Shown only when errors/warnings exist
- **Publish status:** Shown only during/after publish

## 10. Overlay Rendering Priority

Overlays stack in a deterministic z-order. Higher-numbered layers render above lower ones:

```
 1. Base Map (OSM tiles)
 2. Entity layers (buildings, roads, rooms, nodes, edges)
 3. Hover indicator
 4. Selection highlight
 5. Preview geometry (in-progress drawing)
 6. Editing handles (vertex, transform)
 7. Validation markers
 8. Tool overlays (measurement labels, snap indicators)
 9. Confirm Panel (floating bar at canvas bottom)
10. Context menus
11. Tooltips
```

No component may hardcode a z-index outside this stack. All overlay components declare their position in this priority order.

## Implementation Boundaries

This document specifies **interaction behavior only**. It intentionally does not prescribe:

- React components, hooks, or state management
- CSS, styling, or layout implementation details
- MapLibre-specific rendering techniques
- Data fetching, caching, or persistence strategies

Those belong to implementation plans (M3.4B) and are governed by the service architecture established in M3.3 and ADR 0015.

## Interaction Invariants

These invariants summarize the interaction architecture and serve as a quick reference for future decisions:

1. **Exactly one primary tool is active at all times.**
2. **Selection survives tool changes.** Switching tools never clears selection.
3. **Preview always precedes mutation.** No editing operation modifies `CampusDocument` without entering Preview first.
4. **Every mutation is a Command.** No UI component, tool, or service mutates `CampusDocument` directly.
5. **The Context Panel never owns data.** It resolves from editor context and renders editors—it never stores or manages state.
6. **The Status Bar never owns state.** It is a read-only projection of editor state.
7. **The Canvas never owns interaction.** It renders and hit-tests. The active tool interprets input.
8. **The Explorer never owns selection.** It displays the entity tree and dispatches select commands. `SelectionManager` owns selection state.
9. **Commands never modify derived artifacts.** Only `CampusDocument` may be modified by commands. NavigationGraph, validation results, and publish artifacts are recomputed by their owning services.

## Completion Criteria

M3.4.1 is complete when:

1. Single editor route (`/studio/[id]/edit`) with no separate Floor Editor route
2. Context Panel implemented with registry-driven resolver
3. Workflow Card integrated into Context Panel (not a separate page)
4. Status Bar implemented with persistent and transient elements
5. Canvas context menu implemented (entity-specific)
6. Selection unified through `SelectionManager` with bidirectional highlighting
7. `ShortcutRegistry` service implemented with core shortcuts
8. Confirm Panel workflow documented and implemented across all creation/modification tools
9. Interaction pipeline preserved: Input → Controller → Tool → Preview → Confirm → Command → Document → Render
