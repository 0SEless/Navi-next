# M3.4.2 — Selection System Specification

**Status:** Accepted
**Date:** 2026-07-12
**Dependencies:** M3.4.1 (Editor Interaction & Workspace Specification), ADR 0015 (Service Boundaries)

---

## 1. Purpose

Selection is a cross-cutting concern in NAVI Studio. Every major UI surface (Canvas, Explorer, Context Panel, Status Bar, Workflow) reads from or reacts to the current selection. This document defines the complete selection architecture: the `SelectionManager` API, the event contract, the focus model, multi-selection, the canvas rendering contract, and the `SelectionBridge` deprecation plan.

This is the canonical reference for how selection works in the editor. Any component that reads, writes, or reacts to selection must conform to this specification.

---

## 2. Selection Principles

1. **Selection is scoped to the active CampusDocument.** Opening another document destroys the current selection and creates a new selection state. Selection is never global — it belongs to the editing session and its document.
2. **Selection is the single source of truth for entity targeting.** All UI components consume from `SelectionManager`. Nothing else owns selection.
3. **Focus is not selection.** Focus (viewport navigation context) is owned by `ViewportManager`. Selection and focus are independent states that can coexist.
4. **Hover is not selection.** Hover (pointer-precise cursor state) is owned by `PointerManager`. Selection and hover are independent states managed by different subsystems.
5. **Rendering never owns selection state.** The Canvas renders highlights based on selection events. It never stores, caches, or derives selection state.
6. **Selection survives tool changes.** Switching from Select to Draw Room does not clear selection. Only explicit clear actions (click empty space, Escape, entity deletion, new document) clear it.
7. **Commands operate on the current selection.** Delete, Duplicate, Move, Rename, Properties — all target the selection set unless the active tool explicitly overrides the target.
8. **Selection state is immutable outside SelectionManager.** No service, tool, or UI component may directly mutate the selection set. All changes go through `select()`, `toggle()`, or `clear()`.

## 3. Selection Architecture

### Subsystem Ownership

| State | Owned By | Description |
|---|---|---|
| **Selection** | SelectionManager | Entity targeting — selected entity IDs, origin, mode |
| **Hover** | PointerManager | Pointer-precise cursor state — entity under cursor, pointer position, modifiers, dragging |
| **Focus** | ViewportManager | Viewport navigation context — active campus/building/floor |

### Selection Flow

```
CampusDocument (scope)
        │
        ▼
Explorer ─┐
Canvas ───┼──→ SelectionManager ──→ selection.changed ──→ Canvas
Keyboard ─┘         │                selection.cleared      Explorer
Programmatic         │                selection.focusReq.    Context Panel
                     │                                       Status Bar
                     │                                       Workflow
                     │
              ViewportManager (consumes focusRequested,
                                decides camera movement)
```

`SelectionManager` is the sole owner of selection state. Every UI surface is a consumer. Nothing reads selection from any other source.

### Ownership Diagram

```
                CampusDocument
                     │
                     ▼
            SelectionManager
                     │
                     ▼
            SelectionSnapshot
                     │
        ┌────────────┼────────────┐
        ▼            ▼            ▼
     Canvas    Context Panel  Workflow
   Explorer     Status Bar   Viewport
```

Nothing writes below `SelectionManager`. Everything below it only reads.

### PointerManager (New Subsystem)

`PointerManager` owns all pointer-related state that was previously conflated with selection.

```typescript
class PointerManager {
  /** Entity under the cursor (or null). Updates at pointer-move rate. */
  get hoveredSelector(): EntitySelector | null
  get hoveredEntityId(): string | null

  /** Current pointer position in screen coordinates. */
  get pointerPosition(): { x: number; y: number } | null

  /** Current pointer position in world (map) coordinates. */
  get worldPosition(): { lng: number; lat: number } | null

  /** Whether the pointer is currently pressed. */
  get isPressed(): boolean

  /** Whether the pointer is currently dragging. */
  get isDragging(): boolean

  /** Active modifier keys at pointer time. */
  get modifiers(): { ctrl: boolean; shift: boolean; alt: boolean; meta: boolean }
}
```

`PointerManager` emits:

- `pointer.hoverChanged` — when the entity under cursor changes. Payload: `{ hoveredSelector, hoveredEntityId }`.
- `pointer.modifiersChanged` — when modifier key state changes.

The Canvas Renderer subscribes to `pointer.hoverChanged` for hover highlights, and to `selection.changed` for selection highlights. These are independent subscriptions.

### Event Types

| Event | Emitted By | Emitted When | Payload |
|---|---|---|---|
| `selection.changed` | SelectionManager | Selection set modified (select, toggle, clear, replace) | `{ entityIds, lastSelectedId, selectors, lastSelectedSelector, mode, origin }` |
| `selection.cleared` | SelectionManager | Selection explicitly cleared | `{ origin }` |
| `selection.focusRequested` | SelectionManager | A specific entity should become the viewport focus | `{ entityId, selector, origin }` |
| `pointer.hoverChanged` | PointerManager | Entity under cursor changes | `{ hoveredSelector, hoveredEntityId }` |
| `pointer.modifiersChanged` | PointerManager | Modifier key state changes | `{ ctrl, shift, alt, meta }` |

`selection.cleared` is a subset of `selection.changed`, emitted separately so consumers that only care about empty-→non-empty transitions can listen without filtering.

## 4. Selection API

### Public Methods

```typescript
class SelectionManager {
  // ── Mutators ──────────────────────────────────────────────

  /** Replace selection with a single entity. */
  select(input: SelectionInput, origin?: SelectionOrigin): void

  /** Add or remove an entity from the selection set (multi-select). */
  toggle(input: SelectionInput, origin?: SelectionOrigin): void

  /** Clear all selection. */
  clear(origin?: SelectionOrigin): void

  /** Replace the entire selection set (from programmatic restore, marquee result). */
  replace(inputs: SelectionInput[], origin?: SelectionOrigin): void

  // ── Queries ───────────────────────────────────────────────

  isSelected(id: string): boolean

  get selectedIds(): string[]
  get selectors(): EntitySelector[]
  get count(): number
  get lastSelectedId(): string | null
  get lastSelectedSelector(): EntitySelector | null

  get entityIds(): ReadonlySet<string>

  // ── State ─────────────────────────────────────────────────

  /** Immutable snapshot of the full selection state. */
  get snapshot(): SelectionSnapshot

  /** Monotonically increasing revision counter. Bumps on every mutation. */
  get revision(): number

  /** Subscribe to state changes (for useSyncExternalStore). */
  onChange(fn: () => void): () => void
}
```

### Removed / Deprecated in M3.4.2

| Method | Reason | Replacement |
|---|---|---|
| `resetOnToolChange()` | Contradicts M3.4.1 invariant (selection survives tool changes). | Remove. |
| `state` (LegacySelectionState) | Superseded by `snapshot`. | Use `snapshot` directly. |
| `setMode(mode)` | Mode is derived, not set externally. | Remove. SelectionManager detects mode internally based on selection origin and input patterns. |
| `setHover` / `clearHover` | Hover belongs to PointerManager. | Remove. Use `PointerManager` instead. |
| `boundingBox()` | Selection owns IDs, geometry is owned elsewhere. | Temporarily kept for convenience, but identified as a candidate for `GeometryService.boundingBox(selection)` in M3.5. |

### Event Definitions

```typescript
interface SelectionChangedEvent {
  entityIds: string[]
  lastSelectedId: string | null
  selectors: EntitySelector[]
  lastSelectedSelector: EntitySelector | null
  mode: SelectionMode
  origin: SelectionOrigin
}

interface SelectionClearedEvent {
  origin: SelectionOrigin
}

interface SelectionFocusRequestedEvent {
  entityId: string
  selector: EntitySelector
  origin: SelectionOrigin
}
```

### SelectionSnapshot (Immutable Snapshot)

```typescript
interface SelectionSnapshot {
  /** Currently selected entity selectors (in order of selection). */
  selected: EntitySelector[]

  /** Current selection mode — derived internally from selection origin and input patterns. */
  mode: SelectionMode

  /** Where the last selection originated. */
  origin: SelectionOrigin

  /** The last-selected entity (for context actions). */
  lastSelected: EntitySelector | null
}
```

### Mode Derivation

`SelectionMode` is not set externally. It is derived internally by `SelectionManager`:

- When `select()` is called with no modifier keys → mode = `'single'`
- When `toggle()` is called (Ctrl/Cmd+click) → mode = `'multi'`
- When `replace()` is called with marquee bounds → mode = `'marquee'`

No external code calls `setMode()`. The mode field is a read-only descriptor of how the current selection was assembled.

### Future Extensibility

```typescript
interface SelectionSnapshot {
  // ... current fields ...

  /** Reserved for future use: remote selections, locked entities, AI suggestions. */
  metadata?: Record<string, unknown>
}
```

`metadata` is not used in M3.4.2 but is reserved so that downstream consumers do not need new event subscriptions when features like collaborative cursors, search result selection, or AI suggestions are added in later milestones.

## 5. Selection Lifecycle

### Event Ordering (Frozen)

Every mutation follows this exact ordering:

```
1. Mutate internal state (entityIds, entitySelectors, lastSelected)
2. Purge stale entity IDs that no longer exist in CampusDocument
3. Infer mode from mutation path (single / multi / marquee)
4. Bump revision counter
5. Freeze SelectionSnapshot
6. Emit event(s) to eventBus (selection.changed, selection.cleared, selection.focusRequested)
7. Fire onChange subscribers (for useSyncExternalStore)
```

This ordering is frozen. Consumers may rely on:
- The snapshot being consistent before any event fires.
- The revision having incremented before subscribers are notified.
- All events for a single mutation being emitted synchronously.

### Standard Flow

```
select(input)
    │
    ├─ 1. clear internal state
    ├─ 2. add input, set lastSelected
    ├─ 3. purge stale
    ├─ 4. infer mode = 'single'
    ├─ 5. bump revision
    ├─ 6. freeze snapshot
    ├─ 7. emit selection.changed
    └─ 8. fire onChange listeners
```

### Toggle Flow

```
toggle(input)
    │
    ├─ 1. if already selected: remove from set, update lastSelected
    │   if not selected: add to set, set as lastSelected
    ├─ 2. purge stale
    ├─ 3. infer mode = 'multi'
    ├─ 4. bump revision
    ├─ 5. freeze snapshot
    ├─ 6. emit selection.changed
    └─ 7. fire onChange listeners
```

### Clear Flow

```
clear()
    │
    ├─ 1. clear internal state
    ├─ 2. purge stale (no-op, already empty)
    ├─ 3. infer mode = 'single' (reset to default)
    ├─ 4. bump revision
    ├─ 5. freeze snapshot
    ├─ 6. emit selection.cleared
    ├─ 7. emit selection.changed (with empty sets)
    └─ 8. fire onChange listeners
```

### Selection Integrity

After every mutation, `SelectionManager` verifies that all selected entity IDs exist in `CampusDocument`. Any ID not found in the document tree is silently removed from the selection set. This prevents stale selections from surviving entity deletion or document replacement.

## 6. Focus Model

Focus is the **viewport navigation context** — it answers "what part of the document is the user looking at?" It is distinct from selection.

| State | Owned By | Purpose | Example |
|---|---|---|---|
| **Selection** | SelectionManager | Entity targeting | Room 204 is selected |
| **Focus** | ViewportManager | Viewport context | Floor 2 is the active floor |

### Focus Flow

```
SelectionManager.select(entity, origin=Explorer)
    │
    ├─ emit selection.changed
    └─ emit selection.focusRequested { entityId, origin }
            │
            ▼
        ViewportManager
            │
            ├─ if origin=Canvas: ignore (user is already looking)
            ├─ if origin=Explorer: ignore (user is already looking)
            ├─ if origin=Keyboard: flyTo if off-screen
            ├─ if origin=Programmatic: depends on caller
            └─ update focus state: Campus > Building > Floor
```

ViewportManager owns the focus decision. SelectionManager only requests focus. The focus state is reflected in the Status Bar breadcrumb and Explorer expansion.

## 7. Multi-Selection

### Modes

| Mode | Behavior | Activated By |
|---|---|---|
| `'single'` | Selecting a new entity replaces the selection set. | Default. |
| `'multi'` | Selecting adds to the selection set. `toggle()` adds/removes. | `Ctrl+click` / `Cmd+click` |
| `'marquee'` | Drag on empty canvas selects entities within a bounding rectangle. | Select tool + drag on empty space (M3.5) |

### Multi-Select Rules

- `Ctrl+click` / `Cmd+click` → `toggle()` — add or remove from selection set.
- `Shift+click` (in Explorer) → range select — select all entities between the last selected and the clicked entity.
- `Ctrl+A` → `selectAll()` — select all entities in the current Workspace Context.
- `setMode('multi')` → subsequent `select()` calls accumulate rather than replace.
- `setMode('single')` → next `select()` clears and replaces.

### Multi-Selection Display

When `count > 1`:
- Canvas: show selection highlights on all selected entities.
- Context Panel: show Multi Editor (editable intersection of common properties).
- Status Bar: show `Selected: N`.
- Explorer: show multiple highlighted items.

### Marquee Interface (M3.5 Contract)

```typescript
// Deferred to M3.5. The architectural contract for marquee selection:
// - Activated when Select tool is in 'marquee' mode and user drags on empty canvas.
// - The bounding rectangle is forwarded to a spatial query (CampusDocument spatial index).
// - Results are collected and passed to SelectionManager.replace().
interface MarqueeSelectEvent {
  bounds: { minX: number; minY: number; maxX: number; maxY: number }
  mode: 'replace' | 'add' | 'subtract'
  origin: SelectionOrigin
}
```

## 8. Canvas Rendering Contract

### Responsibilities

The Canvas Renderer (any component that renders selection on the map) must:

1. **Highlight selected entities** — apply a visible indicator (e.g., cyan outline/glow) to every entity in `SelectionSnapshot.selected`.
2. **Update highlights reactively** — subscribe to `selection.changed` and re-apply highlights on every event.
3. **Remove highlights on deselection** — clear the indicator for any entity no longer in the selection set.
4. **Render hover indicator** — show a subtle highlight on the hovered entity. Subscribe to `PointerManager` (via `pointer.hoverChanged`) for hover data; it is no longer part of `SelectionManager`.
5. **Render editing handles** — when a single entity is selected and the active tool is a modification tool, show transform/vertex handles.
6. **Render marquee rectangle** — when in marquee mode and dragging, render the selection rectangle.
7. **Respect overlay priority** — selection renders below editing handles, above entity layers (see M3.4.1 Section 10).

### Prohibitions

The Canvas Renderer must never:

1. **Own or cache selection state.** It reads from `SelectionManager` on every render.
2. **Mutate selection.** No `map.on('click')` handler may call `SelectionManager` directly — the Interaction Controller does that.
3. **Dispatch commands based on selection.** Commands are dispatched by tools and UI, not by the renderer.
4. **Decide camera movement.** The renderer does not call `flyTo`, `easeTo`, or `fitBounds`. Camera ownership belongs to `ViewportManager`.

### Event Flow

```
SelectionManager                          PointerManager
    │                                          │
    ├─ selection.changed                      ├─ pointer.hoverChanged
    │       │                                  │       │
    │       ▼                                  │       ▼
    │   Canvas Renderer                        │   Canvas Renderer
    │       │                                  │       │
    │       ├─ highlight selected              │       └─ update hover indicator
    │       ├─ remove deselected highlights    │
    │       └─ rendering handles               │
    │                                          │
    └─ selection.cleared                       │
            │                                  │
            ▼                                  │
        Canvas Renderer                        │
            │                                  │
            └─ remove all selection highlights ┘
```

## 9. SelectionBridge Deprecation

### Current State

`SelectionBridge` exists as a two-way sync between `SelectionManager` (canonical) and legacy Zustand stores (`useStudioStore`). It is a migration artifact from the pre-M3.2 architecture.

### Migration Timeline

| Phase | What | Status |
|---|---|---|
| M3.3.x | SelectionBridge exists. Both SelectionManager and Zustand stores receive selection updates. | Current |
| M3.4.2 | **Freeze.** No new consumers of `useStudioStore.selectedNodeId` or `useStudioStore.activeBuildingId`. All new components must read from `useSelection()`. | Target |
| M3.5 | **Remove SelectionBridge.** Legacy Zustand stores no longer receive selection updates. All consumers migrated to `useSelection()`. | Future |
| M3.6 | **Delete SelectionBridge source file.** Legacy sync code is removed from the codebase. | Future |

### Migration Rules

- New features must **not** import from `SelectionBridge` or read selection from Zustand.
- Existing legacy consumers may continue reading from Zustand during M3.4, but must be migrated to `useSelection()` before M3.5.
- `SelectionBridge.connect()` and `SelectionBridge.pushExternal()` are deprecated but not removed in M3.4.2.

## 10. Selection Invariants

1. **Exactly one `SelectionManager` exists per editor session.** Created during `createEditorContext()` and injected into the service registry.
2. **Selection is scoped to the active `CampusDocument`.** Opening a new document destroys the current selection state. Selection does not survive document switches.
3. **All UI reads from `SelectionManager`.** No component reads selection from any other source.
4. **Selection survives tool changes.** Switching tools never clears the selection set.
5. **Selection state is immutable outside `SelectionManager`.** No direct mutation of `entityIds`, `entitySelectors`, or any internal field.
6. **Focus is independent of selection.** `ViewportManager` owns focus. `SelectionManager` may request focus, but `ViewportManager` decides camera behavior.
7. **Hover is independent of selection.** `PointerManager` owns hover. `SelectionManager` does not track, store, or emit hover state.
8. **Rendering never owns selection state.** The Canvas Renderer subscribes to events and applies/removes highlights — it does not store, cache, or derive selection.
9. **Commands operate on the current selection** unless the active tool explicitly overrides the target.
10. **Selection events are emitted only after state changes.** Listeners always receive a consistent, post-mutation view.
11. **Every selected entity must exist in `CampusDocument`.** Stale selections are automatically purged on document mutations.

### Invariant Consequences

- The Canvas Renderer must subscribe to both `selection.changed` (selection highlights) and `pointer.hoverChanged` (hover highlight). These are independent subscriptions.
- The Explorer tree highlight uses selection state for bold/active items, and pointer state for the subtle preview-on-hover.
- `PointerManager` never calls `SelectionManager.select()` — the `InteractionController` bridges pointer events to selection mutations.

## 11. Non-Goals

The following are intentionally excluded from M3.4.2:

- MapLibre-specific rendering techniques (`setFeatureState`, layer paint expressions) — belong to implementation plans.
- React component specifications for `SelectionOverlay`, `MultiEditor`, or similar — belong to implementation plans.
- `PointerManager` implementation details (pointer capture, drag thresholds, long-press) — belong to implementation plans.
- `SelectionGeometry` service (extracting bounding boxes from entity geometry) — M3.5.
- Snapping, alignment guides, or transform handles — M3.5.
- Collaborative cursors or remote selection — M4.
- Selection persistence across sessions (saving/restoring selection on document reopen) — future enhancement.
