# M3.4.5 — Input System Specification

**Status:** Accepted
**Date:** 2026-07-12
**Dependencies:** M3.4.1 (Editor Interaction), M3.4.2 (Selection System), M3.4.3 (Tool System), M3.4.4 (Context Panel), ADR 0016 (Active Tool Lifecycle)

---

## 1. Purpose

NAVI Studio currently routes browser events directly from `MapCanvas.tsx` to tools via ad-hoc React event handlers. There is no input abstraction layer: tools receive raw `React.PointerEvent` objects, implement their own drag-threshold detection, handle coordinate transforms individually, and track modifier state from event properties.

M3.4.5 defines the **Input System** — a service layer that sits between browser events and tools. It normalizes input devices, recognizes gestures, resolves coordinate spaces, tracks modifier state, manages pointer capture, and routes the correct event stream to the active tool.

This is the first of two interaction architecture milestones:
- **M3.4.5 — Input System**: answers "what did the user physically do?"
- **M3.4.6 — Shortcut & Command System**: answers "what editor action does that interaction invoke?"

---

## 2. Input System Principles

1. **The Input System is device-agnostic.** Mouse, touch, pen, and future input devices all produce the same `NormalizedPointerEvent`. No tool ever branches on device type.
2. **Gesture recognition is a service, not a tool concern.** Drag thresholds, double-click timing, and click-vs-drag decisions live in the `GestureRecognizer`, not in every tool.
3. **Raw pointers and gestures coexist.** Some tools consume raw `pointerMove` events (vertex editor, brush); others consume `Click`/`Drag` gestures. The `InputRouter` delivers the right stream based on the tool's declared `inputMode`.
4. **Coordinates are resolved once.** The `CoordinateResolver` transforms screen coordinates through map, world, campus, and floor spaces. Tools receive pre-resolved coordinate sets.
5. **Modifier state is a shared service.** `ModifierTracker` owns the canonical state of Shift, Ctrl, Alt, Meta, and Space. No tool or service derives modifier state from event objects.
6. **Focus gates input.** The `InputFocusManager` determines whether events reach tools. A text input or modal dialog suppresses relevant event routing.
7. **The Input System never interprets semantics.** It transforms physical interactions into `EditorInputEvent` values. It does not know what "select" or "draw" means — that belongs to tools and commands.

### Service Summary

| Service | Input | Output | Owns |
|---|---|---|---|
| `InputController` | Browser DOM events | `InputFrame` (includes NormalizedPointerEvent) | DOM listener lifecycle |
| `ModifierTracker` | Keydown/keyup | `ModifierState` + `modifiersChanged` | Canonical modifier state |
| `CoordinateResolver` | Screen coordinates | `CoordSet` (screen, canvas, map, world, floor) | Coordinate transformation |
| `PointerCapture` | Pointer events | Captured pointer delivery | `setPointerCapture` lifecycle |
| `InputFocusManager` | Focus/blur + modal state | `isInputAllowed()` + `focusChanged` | Focus routing rules |
| `GestureRecognizer` | `InputFrame` | Gesture events (Click, Drag, etc.) | Drag threshold, double-click timer |
| `InputRouter` | All input streams | `EditorInputEvent` to tool + `ToolResult` | Event routing logic |

**`InputFrame`** is the immutable snapshot that connects all stages. It is constructed once per browser event and passed read-only to every downstream service.

## 4. NormalizedPointerEvent

The foundational data type. Every input device produces the same shape.

```typescript
interface NormalizedPointerEvent {
  /** Unique pointer ID from the browser (stable for the lifetime of the pointer). */
  pointerId: number

  /** Device-agnostic pointer position relative to the container. */
  screenX: number
  screenY: number

  /** Which button (0 = primary, 1 = middle, 2 = secondary). Normalized. */
  button: number

  /** Bitmask of currently pressed buttons. */
  buttons: number

  /** Device type. */
  pointerType: 'mouse' | 'touch' | 'pen'

  /** Pressure (0–1). 0.5 for mouse, varies for pen/touch. */
  pressure: number

  /** Pen tilt (radians). 0 for mouse/touch. */
  tiltX: number
  tiltY: number

  /** Pen twist (0–359). 0 for mouse/touch. */
  twist: number

  /** Radius of touch contact ellipse (CSS pixels). 0 for mouse. */
  width: number
  height: number

  /** Timestamp of the original browser event. */
  timestamp: DOMHighResTimeStamp
}
```

## 5. InputFrame

Every input event is packaged as an immutable snapshot that all downstream services read from. This ensures deterministic, replayable, and debuggable input processing.

```typescript
interface InputFrame {
  /** The original browser event (for debugging and event forwarding). */
  readonly rawEvent: PointerEvent | WheelEvent | KeyboardEvent

  /** Normalized pointer data (null for keyboard events). */
  readonly pointer: NormalizedPointerEvent | null

  /** Resolved coordinate set for this event. */
  readonly position: CoordSet

  /** Modifier state at the moment this event was processed. */
  readonly modifiers: ModifierState

  /** The DOM element that received the event. */
  readonly target: EventTarget | null

  /** Monotonic frame identifier (increments per event). */
  readonly frameId: number
}
```

**Properties:**

- **Immutable** — all fields are `readonly`. No service may modify an `InputFrame`.
- **Complete** — every coordinate space, modifier, and device property is resolved before the frame leaves the `InputController`.
- **Debuggable** — the `rawEvent` field allows inspector tools to inspect the original browser event.
- **Replayable** — an `InputFrame` stream can be recorded and replayed for regression tests.

The `InputFrame` is constructed in `InputController` after normalization, coordinate resolution, and modifier tracking. It is then passed to `GestureRecognizer`, `InputRouter`, and any other consumer. All consumers see the same snapshot.

### InputFrame Lifetime

An `InputFrame` is created, dispatched, and discarded for a single browser event. No service stores a reference to an `InputFrame` after processing.

```
Browser Event
      │
create InputFrame
      │
dispatch to GestureRecognizer, InputRouter, PointerManager, etc.
      │
discard (eligible for GC)
```

If state must persist between events (gesture recognizer state machine, tool accumulation, drag origin), it belongs in the owning service — never in the `InputFrame`. This prevents stale coordinate bugs and keeps `InputFrame` as a value type.

**Exception:** An input recorder may serialize `InputFrame` objects for replay. A replay system feeds them back through the `InputRouter` without touching `InputController` or the browser event model. Even in this case, each frame is consumed and discarded per event cycle.

Browser event normalization rules:

| Browser Event | Normalized Field Mapping |
|---|---|
| `pointerdown` | `button` as-is, `buttons` updated |
| `pointermove` | `button` unchanged, `buttons` as-is |
| `pointerup` | `button` as-is, `buttons` decremented |
| Touch events | First touch becomes primary pointer. `button` = 0. |

## 6. ModifierTracker

Tracks the canonical state of all modifier keys. Services and tools read from here rather than from individual event objects.

```typescript
interface ModifierState {
  shift: boolean
  ctrl: boolean
  alt: boolean
  meta: boolean
  space: boolean
}

class ModifierTracker extends BaseEditorService {
  readonly id = 'modifierTracker'
  readonly dependencies: readonly string[] = ['eventBus']

  /** Current modifier state snapshot. */
  get state(): ModifierState

  /** Subscribe to changes. */
  on(event: 'modifiersChanged', handler: (state: ModifierState) => void): void
}
```

**Behavior:**

- Subscribes to `keydown`/`keyup` events on the document (not just the canvas) so modifiers are tracked even when focus leaves the editor.
- Batches rapid key events: if a key is pressed and released within the same frame, the `modifiersChanged` event is suppressed.
- Emits `modifiersChanged` when any modifier flips state.
- Resets all modifiers to `false` on `window.blur` (prevents stuck-key state when the user alt-tabs).

All subsequent services in the pipeline attach the current `ModifierState` to every event they emit.

## 7. CoordinateResolver

Transforms screen coordinates through all spatial layers the editor understands.

```typescript
interface CoordSet {
  /** CSS pixels relative to the viewport. */
  screen: { x: number; y: number }

  /** CSS pixels relative to the canvas container. */
  canvas: { x: number; y: number }

  /** MapLibre geographic coordinates. */
  map: { lng: number; lat: number }

  /** Web Mercator world coordinates at current zoom. */
  world: { x: number; y: number }

  /** Canvas pixels at the floor's native resolution (if floor-relative context). */
  floor?: { x: number; y: number }
}

class CoordinateResolver extends BaseEditorService {
  readonly id = 'coordinateResolver'
  readonly dependencies: readonly string[] = ['viewport', 'editingContext']
  readonly provides = ['coordTransform']

  /** Resolve a single screen position through all coordinate spaces. */
  resolve(screenX: number, screenY: number): CoordSet

  /** Pre-compute floor transform for performance (called when floor changes). */
  setFloorTransform(floorId: string, transform: FloorTransform): void
}
```

**Transform chain:**

```
screen (x, y)  — browser viewport
    │
    ▼  offset by container position
canvas (x, y)  — relative to canvas container
    │
    ▼  map.unproject()
map (lng, lat)
    │
    ▼  mercator projection
world (x, y)
    │
    ▼  affine transform (if floor-relative)
floor (x, y)  (optional)
```

The `CoordinateResolver` isolates MapLibre from every downstream consumer. No tool calls `map.unproject()`.

## 8. PointerCapture

Manages pointer capture lifecycle so drag operations survive pointer leave.

```typescript
class PointerCapture extends BaseEditorService {
  readonly id = 'pointerCapture'
  readonly dependencies: readonly string[] = ['eventBus']

  /** The element currently capturing pointer events (or null). */
  get capturedElement(): Element | null

  /** Whether capture is currently active. */
  get isCaptured(): boolean

  /** Initiate capture on the given element. */
  capture(element: Element, pointerId: number): void

  /** Release capture. */
  release(): void

  /** True if the given event's pointerId matches the captured pointer. */
  isCapturedPointer(event: NormalizedPointerEvent): boolean
}
```

**Behavior:**

- On every `pointerdown`, the `InputController` calls `capture(element, pointerId)`.
- On `pointerup` or `pointercancel`, calls `release()`.
- If the browser loses capture (e.g., alert dialog), the service detects it via `pointercancel` and resets internal state.
- Tools never call this service directly. It is managed by the `InputController`.

## 9. InputFocusManager

Determines whether input events should reach tools. Prevents bugs where keyboard shortcuts fire while the user is typing in a text field.

```typescript
type FocusContext = 'canvas' | 'textInput' | 'modal' | 'explorer'

class InputFocusManager extends BaseEditorService {
  readonly id = 'inputFocusManager'
  readonly dependencies: readonly string[] = ['eventBus']

  /** Current focus context. */
  get current(): FocusContext

  /** True if pointer events should be routed to tools. */
  isPointerAllowed(): boolean

  /** True if keyboard events should be routed to tools/shortcuts. */
  isKeyboardAllowed(): boolean

  /** Set the current focus context. */
  setContext(ctx: FocusContext): void

  /** Emitted when focus context changes. */
  on(event: 'focusChanged', handler: (ctx: FocusContext) => void): void
}
```

**Routing rules:**

| Context | Pointer Allowed? | Keyboard Allowed? | Typical State |
|---|---|---|---|
| `canvas` | Yes | Yes | Editor canvas has focus |
| `textInput` | Yes (if outside text field) | No | User typing in a property editor |
| `modal` | No | No | Dialog or modal is open |
| `explorer` | Yes | Partial (enter/space for rename, else no) | Explorer tree is focused |

**Ownership:**

- The `InputFocusManager` does not detect focus changes autonomously. It is a passive service that other components call:
  - `InputController` calls `setContext('textInput')` when a text input receives focus.
  - Modal components call `setContext('modal')` on mount.
  - The canvas shell calls `setContext('canvas')` when the canvas is clicked.
- The `InputRouter` checks `isPointerAllowed()` and `isKeyboardAllowed()` before forwarding events.
- The `ShortcutRegistry` (M3.4.6) also checks `isKeyboardAllowed()` before dispatching commands.

## 10. GestureRecognizer

Converts the raw normalized pointer stream into gesture events. This is a state machine, not a stateless mapper.

```typescript
type GestureEvent =
  | { type: 'click'; frame: InputFrame }
  | { type: 'doubleClick'; frame: InputFrame }
  | { type: 'dragStart'; frame: InputFrame }
  | { type: 'drag'; frame: InputFrame }
  | { type: 'dragEnd'; frame: InputFrame }
  | { type: 'longPress'; frame: InputFrame }

class GestureRecognizer extends BaseEditorService {
  readonly id = 'gestureRecognizer'
  readonly dependencies: readonly string[] = ['coordinateResolver', 'modifierTracker', 'pointerCapture', 'eventBus']
  readonly provides = ['gestureEvents']

  /** Process an InputFrame. May emit 0, 1, or multiple gesture events. */
  process(frame: InputFrame): GestureEvent[]

  /** Configure drag threshold (default: 4px). */
  setDragThreshold(px: number): void

  /** Configure double-click interval (default: 300ms). */
  setDoubleClickInterval(ms: number): void

  /** Subscribe to gesture events emitted by this recognizer. */
  onGesture(handler: (event: GestureEvent) => void): void
}
```

### Gesture State Machine

```
                    pointerdown
IDLE ──────────────────────────────► PENDING_CLICK
  ▲                                       │
  │                              pointerup within threshold
  │                                       │
  │                                  ┌────┴────┐
  │                                  │  within  │  outside
  │                                  │  dblclk  │  dblclk
  │                                  │ interval │  interval
  │                                  ▼         ▼
  │                            PENDING_DBL   CLICK
  │                                  │
  │                              pointerdown
  │                                  │
  │                            PENDING_DBL2
  │                                  │
  │                              pointerup
  │                                  │
  │                              DOUBLECLICK ──► IDLE
  │
  │                              pointermove exceeds threshold
  │                              ───────────────────────────────► DRAGGING
  │                                                                │
  │                                                         pointerup ──► DRAGEND ──► IDLE
  │
  │                              timeout (long press threshold)
  │                              ───────────────────────────────► LONGPRESS ──► IDLE
  │
  pointercancel ──────────────────────────────────────────────► IDLE
```

### Drag Threshold

The drag threshold lives in exactly one place: `GestureRecognizer.dragThreshold`. Default is 4 CSS pixels. Tools do not implement their own thresholds.

```
frame at screen (100, 100)  → pointerdown

  frame at screen (101, 100)  → pointermove, 1px from start → still within threshold → no gesture
  frame at screen (105, 100)  → pointermove, 5px from start → exceeds 4px threshold → dragStart

The threshold is calculated as the Euclidean distance from the pointerdown screen position.
```

### Double-Click Prevention

When a `pointerdown` arrives within the double-click interval after the previous click, the `GestureRecognizer` waits for the second `pointerup` before emitting anything. This prevents the tool from receiving a `click` followed immediately by a `doubleClick` — it receives only `doubleClick`.

## 11. InputController

The single DOM entry point. Owns all event listeners on the editor's canvas container.

```typescript
class InputController extends BaseEditorService {
  readonly id = 'inputController'
  readonly dependencies: readonly string[] = [
    'gestureRecognizer', 'modifierTracker', 'coordinateResolver',
    'pointerCapture', 'inputFocusManager', 'inputRouter', 'eventBus'
  ]

  /** Attach listeners to the given DOM element. Called once during editor mount. */
  attach(element: HTMLElement): void

  /** Detach all listeners. Called during editor unmount. */
  detach(): void

  /** Current pointer state (position, pressed, dragging). */
  get pointerState(): {
    position: { x: number; y: number } | null
    isPressed: boolean
    isDragging: boolean
  }

  /** Build an InputFrame for the current event (called internally for each event). */
  private buildFrame(rawEvent: PointerEvent | WheelEvent | KeyboardEvent): InputFrame
}
```

### Event Handlers

| Browser Event | InputController Action |
|---|---|
| `pointerdown` | Build `InputFrame` (normalize pointer, resolve coordinates, snapshot modifiers). Forward frame to `GestureRecognizer.process()`. Initiate capture via `PointerCapture.capture()`. If tool `inputMode` is `'raw'`, forward frame to `InputRouter.routeRawPointer()`. |
| `pointermove` | Build `InputFrame`. Forward frame to `GestureRecognizer.process()`. If tool `inputMode` is `'raw'`, forward frame to `InputRouter.routeRawPointer()`. |
| `pointerup` | Build `InputFrame`. Forward frame to `GestureRecognizer.process()`. Release capture via `PointerCapture.release()`. If tool `inputMode` is `'raw'`, forward frame to `InputRouter.routeRawPointer()`. |
| `pointercancel` | Reset pointer state. Release capture. Clear gesture state. |
| `wheel` | Build `InputFrame`. Forward to `InputRouter.routeWheel()`. |
| `keydown` | Forward to `ModifierTracker.processKeyDown()`. Modifiers only — non-modifier key routing belongs to M3.4.6. |
| `keyup` | Forward to `ModifierTracker.processKeyUp()`. Modifiers only — non-modifier key routing belongs to M3.4.6. |
| `focusin` / `focusout` | Detect focus target. If text input, call `InputFocusManager.setContext('textInput')`. If canvas, call `setContext('canvas')`. |

## 12. InputRouter

Routes events from the input system to the active tool. This is a thin dispatcher — it never interprets events.

```typescript
class InputRouter extends BaseEditorService {
  readonly id = 'inputRouter'
  readonly dependencies: readonly string[] = [
    'toolRegistry', 'inputFocusManager',
    'gestureRecognizer', 'coordinateResolver', 'modifierTracker', 'pointerCapture', 'eventBus'
  ]

  /** Route a gesture event to the active tool. Returns consumption result. */
  routeGesture(event: GestureEvent, ctx: ToolContext): ToolResult

  /** Route a raw pointer event to the active tool. Returns consumption result. */
  routeRawPointer(event: NormalizedPointerEvent, ctx: ToolContext): ToolResult

  /** Route a wheel event to the active tool. Returns consumption result. */
  routeWheel(event: WheelEventData, ctx: ToolContext): ToolResult
}
```

### Event Reception

The `InputRouter` receives events through two paths:

1. **Gesture events** — subscribes to `GestureRecognizer.onGesture()`. For each gesture, constructs an `EditorInputEvent` and checks routing rules.
2. **Raw pointer events** — called directly by `InputController` via `routeRawPointer()` for each normalized pointer event when the tool's `inputMode` is `'raw'`.
3. **Wheel events** — called directly by `InputController` via `routeWheel()`.

Keyboard events (non-modifier) are **not routed by M3.4.5's InputRouter**. They are consumed by `ModifierTracker` only. Shortcut resolution, tool activation from keys, and command dispatch belong to M3.4.6.

### Routing Logic

```
InputRouter receives an event

  1. Check InputFocusManager.isPointerAllowed()
     → if false → drop event
  2. Read ToolRegistry.activeTool
     → if no active tool → drop event
  3. Read activeTool.inputMode
     → if 'gesture' → forward gesture events only, reject raw pointer events
     → if 'raw' → forward raw events only, reject gesture events
  4. Construct EditorInputEvent from InputFrame + gesture data
  5. Call activeTool.onInput(event, ctx)
  6. Return ToolResult from tool's onInput()
```

### Tool Contract

Tools declare their input consumption pattern. The `InputRouter` reads this to decide which event stream to deliver.

```typescript
interface ToolResult {
  /** True if the tool handled the event and it should not propagate further. */
  handled: boolean
}

interface Tool {
  id: string
  label: string
  cursor?: string
  inputMode: 'gesture' | 'raw'

  onActivate?(ctx: ToolContext): void
  onDeactivate?(ctx: ToolContext): void
  onInput?(event: EditorInputEvent, ctx: ToolContext): ToolResult | void
}
```

**Defaults:**
- If a tool does not set `inputMode`, it defaults to `'gesture'` (the safest default — most tools want click/drag semantics).
- If a tool does not return `ToolResult`, the `InputRouter` assumes `{ handled: false }`.

**Tool input mode by category:**

| Tool | Input Mode | Rationale |
|---|---|---|
| Select | Gesture | Click to select, drag to marquee |
| Pan | Gesture | But actually handled via Space override |
| Draw Building | Gesture | Click to place vertices, double-click to finish |
| Draw Room | Gesture | Drag to create rectangle |
| Draw Road | Gesture | Click to place vertices |
| Draw Hallway | Gesture | Click to place vertices |
| Place Entrance | Gesture | Click wall to place |
| Place Staircase | Gesture | Click to place |
| Place Elevator | Gesture | Click to place |
| Place Panorama | Gesture | Click to place |
| Place QR | Gesture | Click to place |
| Vertex Edit | Raw | Needs per-frame pointerMove during drag |
| Calibrate | Gesture | Click reference points |

## 13. EditorInputEvent

All input reaches the tool through a single `onInput()` method with a discriminated union event type.

```typescript
type EditorInputEvent =
  // ── Raw pointer events ──────────────────────────────
  | { type: 'pointerDown'; frame: InputFrame }
  | { type: 'pointerMove'; frame: InputFrame }
  | { type: 'pointerUp'; frame: InputFrame }

  // ── Gesture events ──────────────────────────────────
  | { type: 'click'; frame: InputFrame; gesture: GestureEvent }
  | { type: 'doubleClick'; frame: InputFrame; gesture: GestureEvent }
  | { type: 'dragStart'; frame: InputFrame; gesture: GestureEvent }
  | { type: 'drag'; frame: InputFrame; gesture: GestureEvent }
  | { type: 'dragEnd'; frame: InputFrame; gesture: GestureEvent }
  | { type: 'longPress'; frame: InputFrame; gesture: GestureEvent }

  // ── Scroll events ───────────────────────────────────
  | { type: 'wheel'; frame: InputFrame; delta: { x: number; y: number; z: number } }
```

### Example Tool Usage

```typescript
const selectTool: Tool = {
  id: 'select',
  label: 'Select',
  inputMode: 'gesture',

  onInput(event: EditorInputEvent, ctx: ToolContext): ToolResult {
    switch (event.type) {
      case 'click': {
        const pos = event.frame.position
        const modifiers = event.frame.modifiers
        const id = ctx.services.spatialQuery.entityAtPosition(pos)
        if (modifiers.shift) {
          ctx.services.selection.toggle(id)
        } else if (id) {
          ctx.services.selection.select(id)
        } else {
          ctx.services.selection.clear()
        }
        return { handled: true }
      }
      case 'dragStart': {
        return { handled: true }
      }
    }
    return { handled: false }
  }
}
```

```typescript
const vertexEditTool: Tool = {
  id: 'vertexEdit',
  label: 'Vertex Edit',
  inputMode: 'raw',

  onInput(event: EditorInputEvent, ctx: ToolContext): ToolResult {
    switch (event.type) {
      case 'pointerDown': {
        this.selectedVertex = this.hitTestVertex(event.frame.position.floor!)
        return { handled: true }
      }
      case 'pointerMove': {
        if (this.selectedVertex) {
          this.selectedVertex.position = event.frame.position.floor!
        }
        return { handled: !!this.selectedVertex }
      }
      case 'pointerUp': {
        if (this.selectedVertex) {
          ctx.services.previewManager.publish({ ... })
          this.selectedVertex = null
        }
        return { handled: true }
      }
    }
    return { handled: false }
  }
}
```

## 14. PointerManager Integration

`PointerManager` (defined in M3.4.2) is a consumer of the Input System. It subscribes to the raw normalized pointer stream to detect hover changes and calls `SpatialQueryService` to determine the entity under the cursor.

```
NormalizedPointerEvent stream
        │
        ▼
PointerManager.onPointerMove(event)
        │
        ├─ Calls SpatialQueryService.entityAtPosition(event.position.map)
        ├─ Updates hoveredEntityId, hoveredSelector
        └─ Emits pointer.hoverChanged
```

The `PointerManager` does not participate in event routing. It reads the normalized pointer stream independently, subscribing via `InputController` or by attaching its own listener to the same event bus.

## 15. Space-Hold Pan Override

The Space-hold Pan override follows the clean separation established in M3.4.5:

1. `ModifierTracker` detects Space keydown/keyup and emits `modifiersChanged`.
2. `ToolRegistry` (not `InputController`) listens for Space changes via `ModifierTracker.on('modifiersChanged', ...)`.
3. When Space becomes held and the current tool is not Pan, `ToolRegistry` stores the previous tool and activates Pan as a temporary override.
4. When Space is released, `ToolRegistry` restores the previous tool.
5. The `InputRouter` continues delivering events to whatever tool is currently active (Pan during Space, previous tool after release).

Flow:

```
keydown Space
    │
    ▼
ModifierTracker
    │  modifiersChanged { space: true }
    ▼
ToolRegistry
    │
    ├─ Stacks current tool as "overridden tool"
    ├─ Activates Pan tool
    └─ InputRouter now routes to Pan
          │
          ▼
keyup Space
    │
    ▼
ModifierTracker
    │  modifiersChanged { space: false }
    ▼
ToolRegistry
    │
    ├─ Deactivates Pan tool
    └─ Restores "overridden tool"
```

**This is enforced by ADR 0016 (Active Tool Lifecycle):** activation goes through CommandDispatcher, temporary override follows the Space+Pan override stack rules.

## 16. Event Flow Examples

### Click to Select

```
User left-clicks on a building

Browser → pointerdown (button: 0, screenX: 400, screenY: 300)
    │
InputController:
    ├─ Builds InputFrame:
    │     pointer: NormalizedPointerEvent { screenX: 400, screenY: 300, ... }
    │     position: CoordSet { screen, canvas, map, world, floor }
    │     modifiers: ModifierState { shift: false, ... }
    │     frameId: 42
    ├─ pointerCapture.capture(element, pointerId)
    └─ gestureRecognizer.process(frame) → [] (no gesture yet, state → PENDING_CLICK)

Browser → pointerup (button: 0, screenX: 400, screenY: 301)
    │
InputController:
    ├─ Builds InputFrame (frameId: 43)
    └─ gestureRecognizer.process(frame) → [click] (within 4px threshold)
    │
InputRouter:
    ├─ tool.inputMode === 'gesture'
    ├─ inputFocusManager.isPointerAllowed() → true
    ├─ Constructs { type: 'click', frame, gesture: { ... } }
    └─ selectTool.onInput({ type: 'click', frame, gesture }, ctx) → { handled: true }
        └─ id = spatialQuery.entityAtPosition(frame.position)
        └─ selection.select(id)
```

## 19. Implementation Boundaries

## 20. Input System Invariants

1. **Exactly one input pipeline serves all tools.** No tool registers its own DOM event listeners.
2. **Tools never receive raw browser `PointerEvent` objects.** They receive `EditorInputEvent` containing an `InputFrame`.
3. **No tool implements its own drag threshold.** The `GestureRecognizer` owns all threshold logic.
4. **No tool calls `map.unproject()`.** The `CoordinateResolver` owns all coordinate transforms.
5. **No tool reads `event.shiftKey` from a pointer event.** All modifier state comes from `ModifierTracker`.
6. **Focus always gates input.** The `InputFocusManager` is checked before any event reaches a tool.
7. **Every input event produces exactly one `InputFrame`.** All services consume the same immutable snapshot.
8. **Every `onInput()` returns a `ToolResult`.** Consumption is explicit and deterministic.
9. **The `InputRouter` never interprets events.** It routes. The tool interprets.

## 21. Completion Criteria

M3.4.5 is complete when:

1. `InputController` is the sole DOM event entry point for the editor canvas.
2. All pointer events produce an immutable `InputFrame` containing `NormalizedPointerEvent`, `CoordSet`, and `ModifierState`.
3. `GestureRecognizer` correctly emits Click, DoubleClick, DragStart, Drag, and DragEnd with a configurable drag threshold. Double-click never emits a preceding Click.
4. `CoordinateResolver` resolves screen → canvas → map → world → floor without tools calling MapLibre APIs.
5. `ModifierTracker` tracks all five modifier keys and emits `modifiersChanged`.
6. `PointerCapture` manages capture lifecycle without tool involvement.
7. `InputFocusManager` gates pointer events based on focus context.
8. `InputRouter` reads `tool.inputMode` and delivers the correct event stream to the active tool.
9. All existing tools use `onInput()` with the `EditorInputEvent` discriminated union and return `ToolResult`.
10. No tool in M3.4.5 receives keyboard events (non-modifier). `ModifierTracker` is the only keyboard consumer.
11. Space-hold Pan override follows the ToolRegistry + ModifierTracker flow (not input-layer activation).
12. `PointerManager` reads from the normalized pointer stream for hover detection.
13. No tool registers its own DOM event listener, implements its own drag threshold, or calls `map.unproject()`.
