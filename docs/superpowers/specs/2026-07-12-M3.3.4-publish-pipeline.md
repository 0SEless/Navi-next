# M3.3.4 — Publish Pipeline

**Date:** 2026-07-12
**Status:** Approved
**Milestone:** M3.3 Editor Infrastructure (capstone)

---

## Objective

Add a first-class publish workflow to the editor, completing the three-vertical infrastructure (workflow, validation, publish). Publishing compiles the campus document into navigation artifacts and uploads them for runtime consumption.

---

## Architecture

```
PublishService.publish()
     │
     ├── PREPARING ──→ resolve revision, acquire lock
     ├── VALIDATING ──→ ValidationService.validateNow(); guard
     ├── COMPILING  ──→ NavigationCompiler.compile()
     ├── UPLOADING  ──→ PersistenceService.publish(artifacts)
     └── SUCCESS    ──→ PublishStore stores result
          │
          ▼
     PublishStore -> WorkflowCard (UI)
```

Three new primitives:

| Primitive | Role |
|-----------|------|
| `PublishStore` | State container — publish lifecycle, result, error |
| `PublishService` | Orchestrator — explicit state machine, exclusive lock |
| WorkflowCard integration | Publish step becomes an expandable sub-flow |

## 1. PublishStore

**File:** `packages/editor/src/services/publish-store.ts`

### Types

```ts
type PublishState =
  | 'idle'
  | 'preparing'
  | 'validating'
  | 'compiling'
  | 'uploading'
  | 'success'
  | 'error'

interface PublishResult {
  revision: number               // document version at publish
  compiledGraphVersion: string   // NavigationGraph.version
  campusId: string               // document.metadata.name or unique ID
  artifactCount: number
  nodeCount: number
  edgeCount: number
  startedAt: number              // Date.now() at pipeline start
  finishedAt: number             // Date.now() at pipeline end
  // durationMs derived as finishedAt - startedAt
}

interface PublishSnapshot {
  version: number                // PublishStore mutation counter
  publishState: PublishState
  lastPublishedRevision: number
  lastPublishedAt: number
  publishError: string | null
  publishResult: PublishResult | null
  currentStageStartedAt: number  // for per-stage timing in UI
}
```

### API

```ts
class PublishStore {
  subscribe(listener: () => void): () => void
  getSnapshot(): PublishSnapshot  // frozen, immutable, stable ref

  // Single atomic mutation — PublishService only.
  // Creates ONE immutable snapshot, avoiding intermediate UI states.
  updatePublishState(update: {
    publishState: PublishState
    publishError?: string | null
    publishResult?: PublishResult | null
    lastPublishedRevision?: number
    lastPublishedAt?: number
    currentStageStartedAt?: number
  }): void
}
```

Same reactive pattern as `ValidationStore` / `WorkflowStore` + `WorkflowStore.updateLifecycle()`: frozen snapshots, subscribe/notify, version-based cache invalidation.

## 2. PublishService

**File:** `packages/editor/src/services/publish-service.ts`

### Dependencies

```ts
class PublishService extends BaseEditorService {
  readonly id = 'publish'
  readonly dependencies = ['eventBus', 'documentStore', 'validationService', 'navigationCompiler', 'persistence', 'workflow', 'publishStore']
}
```

Services communicate with services — not with each other's stores.
- `PublishService` depends on `WorkflowService` (not `WorkflowStore`) → calls `workflowService.lastSavedRevision()`
- `PublishService` depends on `ValidationService` (not `ValidationStore`) → calls `validationService.isPending()`, `validationService.hasErrors()`
- Stores are implementation details of their respective services

### Public API

```ts
class PublishService {
  async publish(): Promise<PublishResult>
  getSnapshot(): PublishSnapshot
  isPublishing(): boolean
  lastPublishedRevision(): number | null
}
```

### Exclusive lock

Promise-based instead of boolean:

```ts
private currentPublishPromise: Promise<PublishResult> | null = null

async publish(): Promise<PublishResult> {
  if (this.currentPublishPromise) return this.currentPublishPromise
  this.currentPublishPromise = this.runPublish()
  try { return await this.currentPublishPromise }
  finally { this.currentPublishPromise = null }
}
```

Multiple button clicks await the same in-flight publish.

### Centralized guards

```ts
private assertCanPublish(): void {
  if (this.isPublishing()) throw new Error('Already publishing')
  if (this.validationService.isPending()) throw new Error('Validation in progress')
  if (this.workflowService.isSaving()) throw new Error('Save in progress')
  if (this.workflowService.hasUnsavedChanges()) throw new Error('Document has unsaved changes')
}
```

Guards use service-level queries, not raw store inspection. Stores are implementation details.

### Private transition helper

```ts
private transition(state: PublishState): void {
  this.publishStore.updatePublishState({
    publishState: state,
    currentStageStartedAt: Date.now(),
  })
}
```

Automatically sets `currentStageStartedAt` for per-stage timing and clears previous errors on state change. Single call site keeps `runPublish()` readable.

### State machine (`runPublish()`)

```
runPublish()

↓

assertCanPublish()                      // guard — throws if preconditions fail

↓

transition(PREPARING)
  → resolve revision from documentStore.version
  → record startedAt

↓

transition(VALIDATING)
  → if validationService.lastValidatedRevision() < documentStore.version:
      await validationService.validateNow()
  → else: reuse cached validation result
  → if validationService.hasErrors() → fail('Validation failed')

↓

transition(COMPILING)
  → await navigationCompiler.compile()
  → if error → fail(compileResult.message)

↓

transition(UPLOADING)
  → await persistence.publish(compileResult.artifacts!)
  → if error → fail(publishResult.message)

↓

transition(SUCCESS)
  → build PublishResult from compileResult + timing
  → publishStore.updatePublishState({
      publishState: 'success',
      publishResult: { ... },
      lastPublishedRevision: revision,
      lastPublishedAt: Date.now(),
    })
```

Every transition calls the private `transition()` helper which atomically updates PublishStore. No intermediate states exposed.

### Error recovery

- On failure, `updatePublishState({ publishState: 'error', publishError: reason })`
- User must dismiss before retrying
- No auto-retry

### WorkflowService changes

- **Remove** `WorkflowService.publish()` entirely
- WorkflowCard "Publish" button calls `PublishService.publish()` directly

## 3. Publish Panel (WorkflowCard integration)

**No standalone panel.** The publish UI lives inside the existing WorkflowCard.

### Current WorkflowCard layout

```
┌─────────────────────────────────────┐
│ Workflow                            │
│                                     │
│ Validate     [Validate]             │
│ Compile      [Compile]              │
│ Save         [Save]                 │
│ Publish      [Publish]              │
│ ─────────────────────────────────── │
│ Next: Validate your campus          │
└─────────────────────────────────────┘
```

### New WorkflowCard layout

The "Publish" step row expands to show a sub-flow when active:

**Idle:**
```
│ Publish      [Publish]             │
│              Never Published        │
```

**Publishing (expanded):**
```
│ Publish      ████████░░░░ 68%      │
│  ✓ Validating                       │
│  ✓ Compiling (120ms)                │
│  ▷ Uploading                        │
```

**Success (collapsed):**
```
│ Publish      ✓ Published v42        │
│              3 artifacts · 430ms    │
│              [Publish]              │
```

**Error (expanded):**
```
│ Publish      ✗ Failed               │
│  ✗ Compilation error                │
│    "Missing building footprint"      │
│              [Dismiss] [Open Problems]│
```

### `usePublish()` hook

Follows the same pattern as `useWorkflow()`:

```ts
function usePublish(): {
  snapshot: PublishSnapshot
  publish: () => Promise<void>
  isPublishing: boolean
  dismissError: () => void
}
```

Uses `useSyncExternalStore` to subscribe to PublishStore, same as `useWorkflow()` subscribes to WorkflowStore.

### Implementation approach

- `WorkflowCard` uses `usePublish()` hook (not direct service lookup)
- `computeProgress()` updated to derive publish sub-steps from `PublishState`
- The publish row conditionally renders progress/details based on `PublishStore` state
- Publish button calls `publishService.publish()` via the hook
- "Open Problems" navigates to Problems panel

```ts
registry.register('publishStore', publishStore)
registry.register('publish', publishService)
```

Service ID is `'publish'` (not `'publishService'`), matching the `'workflow'` / `'autosave'` convention.

## 5. Out of scope (deferred)

Deliberately excluded from this milestone:

- Git-style version history browser
- Version rollback / roll forward
- Release notes / changelog
- Multiple environments (staging / production)
- Publish queue / scheduling
- CI/CD integration
- Diff viewer between publishes
- Team approvals / permissions
- `LifecycleStore<TState, TResult>` abstraction (deferred to M4)

### Non-goal: cancellation

Publish cannot be cancelled once started. No `AbortController` or cancel mechanism. If the user needs to abort, they wait for completion or error. This keeps the state machine simple and prevents partial artifact uploads.

## 7. Success criteria

1. `PublishStore` stores and exposes publish lifecycle state as frozen snapshots
2. `PublishService.publish()` runs the full validate→compile→upload pipeline as an explicit state machine
3. Pipeline failures are caught, atomically stored, and surfaced in the UI
4. Promise-based exclusive lock: multiple clicks await the same in-flight publish
5. `assertCanPublish()` centralizes all precondition guards (dirty/saving/validating/already publishing)
6. Validation is cached: if `lastValidatedRevision === document.version`, reuses result
7. WorkflowCard shows publish progress (per-stage indicators, timing via `currentStageStartedAt`)
8. WorkflowCard shows publish results (revision, artifact counts, `startedAt`/`finishedAt`)
9. `WorkflowService.publish()` removed — no dead code
10. `usePublish()` hook follows same pattern as `useWorkflow()`
11. `PublishStore.updatePublishState()` is the single atomic mutation — no intermediate states
12. `PublishService` never mutates `CampusDocument` — it is read-only with respect to the document
13. All existing tests pass; PublishService tests cover: validation failure, compile failure, upload failure, successful publish, concurrent publish, dirty document rejection

---

## 8. Risks and mitigations

| Risk | Mitigation |
|------|------------|
| Compilation is slow for large campuses | Per-stage progress in UI; compile runs async |
| User clicks Publish multiple times | Exclusive lock; duplicate clicks are no-ops |
| Validation and publish race | Publish acquires lock; queues behind running validation |
| Persistence adapter not connected | Graceful error; user sees "Publishing not available" |
