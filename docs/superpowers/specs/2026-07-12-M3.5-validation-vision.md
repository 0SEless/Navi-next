# M3.5 — Validation System

**Status:** Accepted
**Date:** 2026-07-12
**Dependencies:** M3.4 (Editor Interaction Platform)

---

## 1. Vision

NAVI Studio needs to answer one question: **"Is this document valid?"**

Without this, users can create disconnected graphs, missing entrances, inaccessible rooms, overlapping geometry, and broken campuses. Validation is the safety net before Compile and Publish — it transforms Studio from a drawing application into a professional CAD/GIS editor.

M3.5 builds a validation pipeline on top of the M3.4 platform. It defines how the editor judges document correctness, surfaces problems, suggests fixes, and adapts to different quality profiles. It is the first milestone that *consumes* the editor platform rather than extending it.

## 2. Architecture

```
CampusDocument
      │
      ▼
ValidationEngine ───────────────► ValidationSnapshot
      │                                 │
      ├── GraphAnalysis                 ├── Issues & Warnings
      ├── GeometryAnalysis              ├── Rule Timings
      ├── MetadataIndex                 ├── Statistics
      ├── SpatialIndex                  ├── Version
      └── Rules                         └── Cached Analyses
                                             │
                                             ▼
      ┌──────────────────────────────────────┼──────────────────────────┐
      │                                      │                          │
      ▼                                      ▼                          ▼
Problems Panel                       Workflow Card                    Publish
(drives selection                   (blocking gate)              (pre-flight check)
 + camera focus)
```

### Key Principles

1. **Validation is externally pull-based, internally event-driven.**
   - Public API: `ValidationEngine.validate(document): ValidationSnapshot`
   - Internal: subscribes to `document.changed`, `entity.created`, `entity.updated`, `entity.deleted`
   - Never subscribes to `CommandDispatcher` — it cares about document state, not commands

2. **Validation never mutates the document.**
   - `ValidationSnapshot` is immutable
   - Auto-fix is a separate consumer that emits commands through `CommandDispatcher`

3. **Rules are independent.**
   - No rule-to-rule dependencies
   - Shared analysis passes (GraphAnalysis, GeometryAnalysis, etc.) compute reusable results once
   - Rules consume analysis results, not other rules' output

4. **ValidationSnapshot is the canonical validation state of CampusDocument.**
   - Problems Panel, Workflow Card, Publish, and Context Panel all consume the same snapshot
   - No other subsystem creates its own issue list or validation cache
   - Nobody re-validates unless necessary
   - Snapshot includes document identity: `documentId`, `documentVersion`, `profile`, `validatedAt`

5. **Profiles are rule metadata.**
   - Each rule declares which profiles it belongs to: `['draft', 'publish', 'strict']`
   - Profiles can override rule configuration (e.g., tolerance thresholds)

6. **Validation is deterministic.**
   - Given the same `CampusDocument`, `profile`, and configuration, validation always produces the same `ValidationSnapshot`
   - No dependence on editor state, UI, tool context, or randomness
   - Makes testing trivial: snapshot assertions are pure function tests

## 3. Component Classification

| Component | Category | Justification |
|---|---|---|
| ValidationEngine | Core Service | Long-lived, owns independent state (ValidationSnapshot), used by multiple subsystems |
| Rule System | Internal Helper (of ValidationEngine) | Rules are plugins, but the framework lives inside ValidationEngine |
| Analysis Passes | Internal Helper (of ValidationEngine) | GraphAnalysis, GeometryAnalysis — private to the engine |
| Problems Panel | Feature Module | Self-contained UI feature built on the platform |
| Auto Fix | Feature Module | Self-contained capability, dispatches commands |
| Validation Profiles | Configuration | Rule metadata + settings, not a service |

## 4. Sub-specs

| Spec | Scope | Priority |
|---|---|---|
| M3.5.1 — Validation Engine | Core service, ValidationSnapshot, document change subscriptions, cache lifecycle | 1 |
| M3.5.2 — Rule Framework | Rule interface, analysis passes, rule registration, built-in rule set | 1 |
| M3.5.3 — Problems Panel | Dedicated panel UI, issue navigation (select → focus), severity display | 2 |
| M3.5.4 — Auto Fix | AutoFixRegistry, fix providers, command generation, undo support | 3 |
| M3.5.5 — Incremental Validation | Change tracking, affected rule mapping, partial re-validation | 2 |
| M3.5.6 — Validation Profiles | Profile definitions, rule sets, config overrides, UI for switching | 3 |

Priority 1 = define architecture (must agree early)
Priority 2 = core user-facing value
Priority 3 = polish

## 5. First Rule Set

### Graph Rules
- Disconnected graph
- Dead-end navigation
- Unreachable destination
- Missing building connection
- Missing floor transition

### Geometry Rules
- Self-intersecting polygon
- Overlapping rooms
- Duplicate vertices
- Invalid winding
- Zero-area polygon

### Accessibility Rules
- Room without entrance
- Floor without vertical access
- Missing accessible route
- Entrance not connected

### Metadata Rules
- Missing name
- Missing code
- Duplicate room number
- Missing category
- Missing QR assignment

### Asset Rules
- Missing panorama image
- Missing QR asset
- Broken media reference

### Publishing Rules
- Missing campus boundary
- No start node
- Empty graph
- No publish profile assigned

## 6. Relationship to Existing M3.3.3 Spec

An earlier `M3.3.3 - Validation Engine & Problems Panel` spec exists from the M3.3 milestone. It contains preliminary thinking on `ValidationRegistry`, `ValidationService`, and debounced validation. M3.5 replaces that spec with:
- The six architectural principles above
- The snapshot-based architecture (vs. one-off validation calls)
- The analysis-pass pattern (vs. rule-to-rule dependencies)
- The Auto Fix framework
- Validation Profiles

---

## 7. Non-Goals (M3.5)

- User-configurable rule creation
- Real-time validation on every keystroke (debounced, not per-key)
- Visualization of validation state on the canvas (post-M3.5, likely M3.8)
- Machine-learning-based problem detection
- External validation plugin API
