# M3.5.6 — Validation Profiles

**Status:** Draft
**Date:** 2026-07-12
**Dependencies:** M3.5.1 (Validation Engine), M3.5.2 (Rule Framework), M3.5.3 (Problems Panel)

---

## 1. Purpose

Validation Profiles decide *which rules run* and *how strictly* for a given context. They are configuration — named sets of rule memberships plus per-profile overrides. They are not a service, not a feature module, and not an editor subsystem. The profile is one of the three inputs to `ValidationEngine.validate(document, profile)` (alongside the document and configuration).

Profiles let the same document be validated lightly while authoring (`draft`), strictly before shipping (`publish`), and exhaustively for QA (`strict`) — without duplicating rules or changing rule definitions.

---

## 2. Architecture

```
ValidationProfile (config)
   │  id, label, rules, overrides
   ▼
ValidationEngine.validate(document, profile)
   │
   ├─ resolve profile → eligible rule set (rule.profiles includes profile)
   ├─ resolve profile → ProfileConfig (tolerances, severity overrides)
   ├─ build ValidationContext { document, profile, analysis, config }
   └─ run eligible rules → ValidationSnapshot
```

- Profiles are consumed by `ValidationEngine`, never by rules directly.
- The active profile is held by the consumer that owns the switcher UI (the Problems Panel). Other consumers pass a profile explicitly (e.g., Publish always requests `'publish'`).
- No profile service exists. Profiles are static configuration data, registered once at boot.

---

## 3. Profile Config

### Strongly typed profile IDs

```typescript
type ValidationProfileId =
  | 'draft'
  | 'publish'
  | 'strict'
```

Every interface that accepts a profile uses this type — never raw `string`. Mistaken `'publish'` vs `'publishh'` is caught at compile time.

### Rule default tolerances

Each rule declares its own default tolerances via a new field on `ValidationRule`:

```typescript
interface ValidationRule {
  readonly ruleId: string
  readonly description: string
  readonly category: string
  readonly defaultSeverity: 'error' | 'warning' | 'info'
  readonly profiles: ReadonlyArray<ValidationProfileId>

  /** Optional default tolerances; merged with profile overrides. */
  readonly defaults?: {
    readonly tolerances?: Readonly<Record<string, number>>
  }

  execute(context: ValidationContext): ReadonlyArray<ValidationIssue>
}
```

The engine performs a two-layer merge at validation time:

```
Rule.defaults.tolerances
        │
        ▼
Profile.tolerances (overrides rule defaults)
        │
        ▼
context.config.tolerances (resolved — passed to all rules)
```

If a rule accesses `context.config.tolerances['geometry.overlapTolerance']`, the engine has already resolved the value: profile value if present, else rule default, else fallback. Rules never coalesce with `??`.

### Severity override handled by engine, not by rules

M3.5.2 defines `defaultSeverity` on each rule. Previously a rule would check `context.config.severityOverrides` and return a different severity. M3.5.6 inverts this:

1. Rule always issues its `defaultSeverity`.
2. After `rule.execute()`, the engine applies profile-level `severityOverrides`:
   ```
   rule returns [{ severity: 'error', ... }]
                  │
                  ▼
   engine checks profile.severityOverrides[rule.ruleId]
                  │
           ┌──────┴──────┐
           ▼              ▼
      override?          no override?
      ↓                  ↓
   issue.severity =      issue.severity =
   override              rule.defaultSeverity
   ```
3. The resulting `ValidationSnapshot` carries the overridden severities.

This means rules never import or think about `severityOverrides`. They emit their natural severity; the engine adjusts downstream. Cleaner separation.

### Future-proof ProfileConfig

```typescript
interface ProfileConfig {
  /** Numeric tolerances keyed by config key, resolved from rule defaults + profile overrides. */
  readonly tolerances: Readonly<Record<string, number>>

  /** Per-rule severity overrides, keyed by ruleId. Resolved by engine post-execution. */
  readonly severityOverrides: Readonly<Record<string, 'error' | 'warning' | 'info'>>

  /**
   * Boolean feature flags for future expansion.
   * e.g. { experimental: true, enableExpensiveChecks: false }
   */
  readonly flags?: Readonly<Record<string, boolean>>
}
```

The `flags` field exists now with no standard keys — it reserves the slot so later additions don't require a structural redesign.

### Extension to ValidationContext (amends M3.5.2 §3)

M3.5.2 defines `ValidationContext` as `{ document, profile, analysis }` and explicitly states that adding configuration is done by adding a field — not changing rule signatures. M3.5.6 adds exactly that field:

```typescript
interface ValidationContext {
  readonly document: CampusDocument
  readonly profile: ValidationProfileId
  readonly analysis: AnalysisCache
  /** Resolved profile configuration. Added by M3.5.6. */
  readonly config: ProfileConfig
}
```

Rules read their tolerances from `context.config.tolerances`. A rule that does not consult `config` simply ignores it — profile overrides are opt-in per rule.

## 4. Built-in Profiles

| Profile | Character | Rule selection | Tolerances |
|---|---|---|---|
| `draft` | **Fast** — core errors only, no expensive checks | Errors only; excludes nitpick warnings and strict geometry checks | Loose (overlap tolerance 2.0, zero-area 0.5 m²) |
| `publish` | **Complete** — all standard rules before Compile/Publish | All `publish`-eligible rules + all errors/warnings | Standard (overlap 1.0, zero-area 0.1 m²) |
| `strict` | **Complete + expensive** — QA exhaustive, future-proof for AI/simulation rules | Every rule including expensive passes (evacuation, AI, simulation — added post-M3.5) | Tight (overlap 0.1, zero-area 0.01 m², enable info-level) |

The engine default (`validate(document)` with no profile) resolves `'default'` → `'draft'` (a `ValidationProfileId`).

### Rule membership

Each rule already declares `profiles: ReadonlyArray<ValidationProfileId>` (amends M3.5.2 §3). The engine runs a rule only when the requested profile is in that array. Profile definitions do not re-list rules; membership lives on the rule. Profiles only supply overrides.

### Severity overrides

A profile may downgrade or upgrade a rule's `defaultSeverity` for that run. The override is applied by the engine after rule execution (see §3), not by the rule itself:

```typescript
// In 'draft', the duplicate-room-number rule is a warning, not an error.
severityOverrides: { 'metadata.duplicateRoomNumber': 'warning' }
```

## 5. Profile Definitions (configuration)

Profiles are defined in a single config module and registered at boot alongside rule providers:

```typescript
interface ValidationProfile {
  readonly id: ValidationProfileId
  readonly label: string
  readonly description: string
  readonly tolerances: Record<string, number>
  readonly severityOverrides?: Record<string, 'error' | 'warning' | 'info'>
}

const PROFILES: ReadonlyArray<ValidationProfile> = [
  draftProfile,
  publishProfile,
  strictProfile,
]

function getProfile(id: ValidationProfileId): ValidationProfile          // throws on unknown
function resolveConfig(profile: ValidationProfile, ruleDefaults?: Record<string, number>): ProfileConfig
```

### Cache key (amends M3.5.1 §5)

The engine's cache key is the triple `(documentVersion, validationEpoch, profile)`. This formalizes what M3.5.1 and M3.5.5 already imply:

| Condition | Effect |
|---|---|
| `documentVersion` changed | Re-validate |
| `validationEpoch` advanced (M3.5.5 base state shift) | Re-validate |
| `profile` changed | Re-validate |
| All three match | Return cached |

The `validationEpoch` field on `ValidationSnapshot` (M3.5.5) participates in cache invalidation alongside `documentVersion` and `profile`.

There is no `freeze()` — profiles are immutable constants, not a mutable registry. Features do not register custom profiles in M3.5 (out of scope, see Non-Goals).

---

## 6. Profile Switching UI

The Problems Panel owns the active profile and renders a profile selector in its header:

```
[ Profiles ]  [ profile: ▼ draft ]  [ Fix all ]  [ re-validate ]
```

- Selecting a profile updates the panel's `activeProfile` and re-pulls: `engine.validate(document, activeProfile)`.
- The selector lists the built-in profiles by `label`.
- The selected profile is panel-local UI state, not editor-global state.
- Publish and Workflow Card ignore the panel's selection — they request `'publish'` explicitly.

Switching profile changes the cache key (`documentVersion` + `profile`), so the engine returns a fresh snapshot (M3.5.1 §5). No command is needed for switching; it is a pure view/request change.

---

## 7. Determinism

Validation remains a pure function of `(document, profile, configuration)`. Given the same three inputs, `validate()` always returns an equivalent snapshot. Profile config is static, so it adds no hidden state.

---

## 8. Implementation Freeze

No new architectural abstractions may be introduced during implementation unless they solve a real problem encountered in code. Specifically:

- No `ProfileManager`, `ProfileService`, or `ProfileRegistry` class
- No singleton or global for the active profile (it is panel-local UI state)
- No rule-level imports of the profile system (rules receive only `context.config`)
- No runtime registration of custom profiles (the built-in set is frozen for M3.5)

If an implementation difficulty arises, the fix should be *removing* abstraction, not adding it.

---

## 9. Non-Goals (M3.5.6)

- User-creatable or plugin-registered profiles
- Per-document profile persistence (saved with the campus file)
- Profile-specific rule *logic* (profiles tune, never replace, rule code)
- A profile service or manager subsystem
- Visualizing profile state on the canvas

---

## 10. Completion Criteria

M3.5.6 is complete when:

1. `ValidationProfileId` type exists: `'draft' | 'publish' | 'strict'`. All profile-aware interfaces use it.
2. `ValidationProfile` config type exists with `id: ValidationProfileId`, `label`, `description`, `tolerances`, and optional `severityOverrides`.
3. `ValidationRule` includes `defaults?: { tolerances? }` for rule-level tolerance defaults.
4. Engine performs a two-layer merge: `Rule.defaults.tolerances` → `Profile.tolerances` → resolved `ProfileConfig.tolerances`.
5. `ProfileConfig` typed with `tolerances`, `severityOverrides`, and `flags?` for future expansion.
6. After `rule.execute()`, the engine applies severity overrides from the profile — rules never change their own severity.
7. `ValidationContext` includes `config: ProfileConfig` (amends M3.5.2 §3).
8. Built-in profiles `draft` (fast), `publish` (complete), `strict` (complete + expensive) defined as static configuration.
9. Cache key is `(documentVersion, validationEpoch, profile)` — amends M3.5.1 §5.
10. Problems Panel renders a profile selector and re-pulls validation on change.
11. Publish / Workflow Card request `'publish'` independently of the panel selection.
12. Validation stays deterministic across `(document, profile, configuration)`.
13. No `ProfileManager`, `ProfileService`, or `ProfileRegistry` exists — profiles are constants.
