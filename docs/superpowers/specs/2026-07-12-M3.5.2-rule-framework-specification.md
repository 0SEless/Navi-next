# M3.5.2 — Rule Framework

**Status:** Accepted
**Date:** 2026-07-12
**Dependencies:** M3.5.1 (Validation Engine), CampusDocument

---

## 1. Purpose

The Rule Framework defines how validation rules and analysis passes are defined, registered, and executed. It lives inside `ValidationEngine` as an internal subsystem — the engine orchestrates, the rules validate.

---

## 2. Architecture

```
ValidationEngine
       │
       ▼
┌──────────────────────┐
│    Analysis Pipeline  │  ← AnalysisPass[]
│                      │
│  GraphAnalysis       │
│  GeometryAnalysis    │
│  MetadataIndex       │
│  SpatialIndex        │
└──────────┬───────────┘
           │
           ▼
┌──────────────────────┐
│    AnalysisCache     │  ← single-use container
│                      │
│  { graph, geometry,  │
│    metadata, spatial }│
└──────────┬───────────┘
           │
           ▼
┌──────────────────────┐
│    Rule Engine        │  ← ValidationRule[]
│                      │
│  For each rule:      │
│    1. profile match  │
│    2. execute        │
│    3. collect issues │
└──────────┬───────────┘
           │
           ▼
┌──────────────────────┐
│  ValidationSnapshot   │
│  (issues + analysis   │
│   cache + state)      │
└──────────────────────┘
```

Analysis passes run first, once. Rules consume their results. Both are registered into the engine via `RuleProvider`.

## 3. ValidationRule

```typescript
interface ValidationRule {
  readonly ruleId: string
  readonly description: string
  readonly category: string
  readonly defaultSeverity: 'error' | 'warning' | 'info'
  readonly profiles: ReadonlyArray<string>

  execute(context: ValidationContext): ReadonlyArray<ValidationIssue>
}
```

### ValidationContext

```typescript
interface ValidationContext {
  readonly document: CampusDocument
  readonly profile: string
  readonly analysis: AnalysisCache
}
```

The context object future-proofs the execute signature. Adding a new parameter (cancellation token, timing service, configuration) adds a field to `ValidationContext` instead of changing every rule's signature.

### Principles

- **Rules are independent.** No rule references another rule's output. All shared computation lives in analysis passes.
- **Rules are deterministic.** Same context → same issues, always.
- **Rules do not mutate.** They read `CampusDocument` and `AnalysisCache` and return issues. No side effects.
- **Rules declare their profiles.** The engine skips rules whose `profiles` don't include the requested profile.
- **Rules are stateless.** A rule instance is created once and reused across validation runs. Any per-run state belongs in analysis passes.

### Example

```typescript
class DisconnectedGraphRule implements ValidationRule {
  readonly ruleId = 'graph.disconnected'
  readonly description = 'Detects disconnected subgraphs'
  readonly category = 'graph'
  readonly defaultSeverity = 'error'
  readonly profiles = ['draft', 'publish', 'strict']

  execute(context: ValidationContext): ValidationIssue[] {
    const graph = context.analysis.graph
    if (!graph || graph.connectedComponents.length <= 1) return []

    return graph.connectedComponents.slice(1).map(component => ({
      issueId: `graph.disconnected.${component.nodes[0]}`,
      ruleId: this.ruleId,
      severity: this.defaultSeverity,
      message: `Disconnected subgraph detected (${component.nodes.length} nodes)`,
      targets: component.nodes.map(id => ({ entityId: id, entityType: 'node' })),
    }))
  }
}
```

## 4. Analysis Passes

Analysis passes compute expensive results once and share them across all rules.

```typescript
interface AnalysisPass<T> {
  readonly produces: string
  readonly description: string

  execute(document: CampusDocument): T
}
```

The `produces` string becomes the key in `AnalysisCache`. For example, a pass with `produces: 'graph'` writes to `cache.graph`.

### AnalysisCache

Immutable once constructed. No rule can mutate analysis results.

```typescript
interface AnalysisCache {
  readonly graph?: GraphAnalysis
  readonly geometry?: GeometryAnalysis
  readonly metadata?: MetadataIndex
  readonly spatial?: SpatialIndex
}
```

### Built-in Passes

| Pass | produces | Emits | Consumed By |
|---|---|---|---|
| Graph Analysis | `graph` | connected components, reachability, orphan nodes | Graph rules, Accessibility rules |
| Geometry Analysis | `geometry` | polygon validity, overlap detection, winding | Geometry rules |
| Metadata Index | `metadata` | name index, code index, category index | Metadata rules |
| Spatial Index | `spatial` | spatial tree for proximity queries | Geometry rules, Accessibility rules |

### Pass Lifecycle

1. Engine calls `validate(document, profile)`
2. Engine runs all registered analysis passes: each pass receives the document, returns its result
3. Results are collected into `AnalysisCache`
4. Engine runs rules, passing the same `AnalysisCache` to each
5. Snapshot is built with `AnalysisCache` included

When incremental validation (M3.5.5) is added, analysis passes that depend on unchanged data can be skipped.

## 5. RuleProvider

Mirrors the `ShortcutProvider` pattern from M3.4.6. Features own their rules.

```typescript
interface RuleProvider {
  readonly providerId: string
  registerRules(registry: RuleRegistry): void
}

interface RuleRegistry {
  registerRule(rule: ValidationRule): void
  registerAnalysisPass<T>(pass: AnalysisPass<T>): void
  freeze(): void
}
```

### Example

```typescript
class GraphValidationModule implements RuleProvider {
  readonly providerId = 'validation.graph'

  registerRules(registry: RuleRegistry): void {
    registry.registerAnalysisPass(new GraphAnalysisPass())
    registry.registerRule(new DisconnectedGraphRule())
    registry.registerRule(new DeadEndNavigationRule())
    registry.registerRule(new UnreachableDestinationRule())
  }
}
```

### Boot Sequence

Registration is boot-only. After initialization, the registry is frozen.

```
Editor Boot
      │
      ▼
registerRuleProvider(graphModule)
registerRuleProvider(geometryModule)
registerRuleProvider(accessibilityModule)
registerRuleProvider(metadataModule)
registerRuleProvider(assetModule)
registerRuleProvider(publishingModule)
      │
      ▼
engine.initialize()  ← calls registry.freeze()
      │
      ▼
Validation begins
```

```typescript
class ValidationEngine extends BaseEditorService {
  /** Boot-only. Calls provider.registerRules(this) immediately. */
  registerRuleProvider(provider: RuleProvider): void
  registerRule(rule: ValidationRule): void
  registerAnalysisPass<T>(pass: AnalysisPass<T>): void

  /** Freezes the registry. After this, register*() calls throw. */
  initialize(): void
}
```

After `initialize()`, any `registerRule()` call throws. This guarantees deterministic rule sets, simplifies testing, and prevents runtime mutations.

## 6. Rule Execution Flow

```
executeRules(document, profile):

  context = { document, profile, analysis: AnalysisCache }
  issues = []
  for each rule in registeredRules:
    if rule.profiles includes profile:
      result = rule.execute(context)
      issues.push(...result)
  return issues
```

```
executeAnalysisPasses(document):

  cache = {}
  for each pass in registeredPasses:
    cache[pass.produces] = pass.execute(document)
  return cache as AnalysisCache
```

The engine makes no guarantees about execution order beyond executing each eligible rule exactly once. This preserves freedom for future optimizations (batching, parallel execution, worker threads) without changing the rule contract.

---

## 7. Profile Filtering

Each rule declares which profiles it belongs to:

```typescript
profiles: ['draft', 'publish', 'strict']
```

When the engine runs with a specific profile, it skips rules that don't include it:

```
Profile: 'draft'

→ runs rules with 'draft' in profiles
→ skips rules with only ['publish', 'strict']
```

A rule with `profiles: ['draft', 'publish', 'strict']` runs in all profiles.
A rule with `profiles: ['publish']` runs only during publish validation.

Rule configuration overrides (from M3.5.6) allow profile-specific tuning without changing the rule definition.

## 8. Built-in Ruleset

The initial rule set organizes into provider modules:

| Module | Rules |
|---|---|
| `validation.graph` | Disconnected graph, Dead-end navigation, Unreachable destination, Missing building connection, Missing floor transition |
| `validation.geometry` | Self-intersecting polygon, Overlapping rooms, Duplicate vertices, Invalid winding, Zero-area polygon |
| `validation.accessibility` | Room without entrance, Floor without vertical access, Missing accessible route, Entrance not connected |
| `validation.metadata` | Missing name, Missing code, Duplicate room number, Missing category, Missing QR assignment |
| `validation.assets` | Missing panorama image, Missing QR asset, Broken media reference |
| `validation.publishing` | Missing campus boundary, No start node, Empty graph |

Each module is a `RuleProvider`. Registration happens at editor startup alongside tool and context registration.

---

## 9. Non-Goals (M3.5.2)

- Rule dependency resolution (rules are independent by design)
- User-defined rules via plugin API
- Rule configuration UI
- Rule performance metrics (tracked in `ValidationStatistics`)

---

## 10. Completion Criteria

M3.5.2 is complete when:

1. `ValidationRule` interface is defined with `ruleId`, `category`, `defaultSeverity`, `profiles`, and `execute(context)`.
2. `ValidationContext` interface provides `document`, `profile`, and `analysis`.
3. `AnalysisPass` interface uses `produces` for cache key assignment.
4. `AnalysisCache` is immutable — all fields are `readonly`.
5. `RuleProvider` interface exists; features register rules via `registerRuleProvider()`.
6. `RuleRegistry` includes `freeze()`; `registerRule()` throws after freeze.
7. `ValidationEngine.initialize()` freezes the registry.
8. Analysis passes run before rules and results are stored in `AnalysisCache`.
9. Profile filtering skips rules whose `profiles` don't include the requested profile.
10. All built-in rules from Section 8 are implemented.
11. Rules are deterministic — same context → same issues.
12. Rules do not mutate the document or analysis cache.
13. No rule-to-rule dependencies exist.
14. The engine makes no guarantee about execution order beyond executing each rule exactly once.
