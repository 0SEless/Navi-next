# M3.5.4 — Auto Fix

**Status:** Accepted
**Date:** 2026-07-12
**Dependencies:** M3.5.1 (Validation Engine), CommandDispatcher, M3.5.3 (Problems Panel)

---

## 1. Purpose

Auto Fix turns a validation issue into a concrete resolution. It is a separate consumer of `ValidationSnapshot` — not part of `ValidationEngine`. Every fix produces one or more commands that flow through `CommandDispatcher`, so fixes inherit undo, redo, and history automatically.

---

## 2. Architecture

```
ValidationEngine
       │
       ▼
ValidationSnapshot (issues carry fixId)
       │
       ▼
┌──────────────────────┐
│   Problems Panel      │  issue with fixId
└──────────┬───────────┘
           │ click "Fix"
           ▼
┌──────────────────────┐
│   AutoFixRegistry     │  fixId → FixProvider
│                      │  buildCommands(issue, context)
└──────────┬───────────┘
           │
           ▼
┌──────────────────────┐
│   CommandDispatcher   │  execute(fixCommand)
└──────────┬───────────┘
           │
           ▼
     CampusDocument mutated
            │
            ▼
     validation cache stale (next request re-validates)
 ```

Auto Fix never mutates the document directly. It produces commands; `CommandDispatcher` applies them.

---

## 3. FixProvider

```typescript
interface FixContext {
  readonly document: CampusDocument
  readonly analyses: AnalysisCache
  readonly snapshot: ValidationSnapshot
}

interface FixResult {
  /** Commands that resolve the issue. */
  readonly commands: ReadonlyArray<Command>

  /** Optional user-facing message about what the fix did. */
  readonly message?: string

  /** Whether the fix requires explicit confirmation before dispatch. */
  readonly requiresConfirmation?: boolean
}

interface FixProvider {
  /** Matches ValidationIssue.fixId. */
  readonly fixId: string

  /** Human-readable label shown on the Fix button. */
  readonly label: string

  /**
   * Priority when multiple providers share a fixId.
   * Higher runs first. Default 0.
   */
  readonly priority?: number

  /** Whether this fix can be applied to the current document state. */
  canApply(issue: ValidationIssue, context: FixContext): boolean

  /** Build the commands that resolve this issue. */
  buildCommands(issue: ValidationIssue, context: FixContext): FixResult

  /** Optional preview; integrates with existing PreviewManager. */
  buildPreview?(issue: ValidationIssue, context: FixContext): FixPreview
}
```

### Principles

- **Fixes are command producers, not document mutators.** A `FixProvider` returns `FixResult.commands`, never calls `document.mutate()` directly.
- **Fixes are stateless.** A provider instance is created once and reused.
- **Fixes are deterministic.** Given the same issue + context, `buildCommands()` returns equivalent commands.
- **Fixes can fail to apply.** `canApply()` returns false when the fix is no longer valid (e.g., the entity was deleted). The UI disables the Fix button.
- **Providers operate only on the supplied `ValidationIssue`.** A fix never searches the document for issues — it receives the issue that triggered it.
- **Providers reuse analysis results.** The `FixContext.analyses` cache is the same one validation computed, so fixes don't rebuild expensive queries.
- **No fix is mandatory.** Issues without a registered `FixProvider` simply show no button.

### Example

```typescript
class ConnectRoadFix implements FixProvider {
  readonly fixId = 'graph.disconnected.road'
  readonly label = 'Connect Road'
  readonly priority = 0

  canApply(issue: ValidationIssue, context: FixContext): boolean {
    return issue.targets.length > 0
      && context.document.entityExists(issue.targets[0].entityId)
  }

  buildCommands(issue: ValidationIssue, context: FixContext): FixResult {
    const roadId = issue.targets[0].entityId
    const nearest = context.analyses.graph?.nearestConnectedNode(roadId)
    return {
      commands: [{
        id: 'road.connect',
        payload: { roadId, targetNodeId: nearest?.id },
      }],
      message: 'Connected road to nearest node',
    }
  }
}
```

## 4. AutoFixRegistry

```typescript
interface FixProviderModule {
  readonly providerId: string
  registerFixes(registry: AutoFixRegistry): void
}

class AutoFixRegistry extends BaseEditorService {
  readonly id = 'autoFixRegistry'
  readonly dependencies: readonly string[] = []

  /** Register a fix provider for a given fixId. */
  registerFix(fix: FixProvider): void

  /** Register all fixes from a module (mirrors RuleProvider). */
  registerFixModule(module: FixProviderModule): void

  /** Get the highest-priority provider for a fixId, or undefined. */
  getFix(fixId: string): FixProvider | undefined

  /** Whether the given issue has an applicable fix in the current document. */
  canFix(issue: ValidationIssue, context: FixContext): boolean
}
```

### Registration

Fix providers register through `FixProviderModule`, mirroring `RuleProvider` and `ShortcutProvider`:

```typescript
autoFixRegistry.registerFixModule(new GraphFixModule())
autoFixRegistry.registerFixModule(new GeometryFixModule())
autoFixRegistry.registerFixModule(new MetadataFixModule())
```

Inside a module:

```typescript
class GraphFixModule implements FixProviderModule {
  readonly providerId = 'fix.graph'

  registerFixes(registry: AutoFixRegistry): void {
    registry.registerFix(new ConnectRoadFix())
    registry.registerFix(new CreateEntranceFix())
  }
}
```

If multiple providers register the same `fixId`, the one with the highest `priority` wins. If priorities tie, the last registration wins (logged as a warning).

## 5. Integration with Problems Panel

The Problems Panel renders a Fix button when an issue's `fixId` resolves to a `FixProvider`:

```
[severity icon] [message]
                 [entity type: name]
                 [Fix] [Fix all]  ← only if fixId registered & canApply()
```

Clicking **Fix** dispatches the single issue's commands:

```typescript
const provider = autoFixRegistry.getFix(issue.fixId)
if (provider?.canApply(issue, context)) {
  const result = provider.buildCommands(issue, context)
  if (result.requiresConfirmation) {
    // Show confirmation dialog
  } else {
    dispatcher.execute(...result.commands)
  }
}
```

Clicking **Fix all** (in the group header) collects fixes for all issues in that group that share the same `fixId`, then dispatches them as a single composite command:

```typescript
const commands: Command[] = []
for (const issue of group.issues) {
  const provider = autoFixRegistry.getFix(issue.fixId)
  if (provider?.canApply(issue, context)) {
    commands.push(...provider.buildCommands(issue, context).commands)
  }
}
// One undo, one history entry
dispatcher.execute(buildCompositeCommand(commands, 'Fix all issues'))
```

This ensures "Fix all" produces a single history entry — undoing once reverts all fixes.

## 6. Fix Result Lifecycle

```
1. User clicks "Fix" on issue
       │
2. AutoFixRegistry.getFix(issue.fixId) → provider
       │
3. provider.canApply(issue, context) → true
       │
4. provider.buildCommands(issue, context) → FixResult
       │
5. dispatcher.execute(...FixResult.commands)
       │
6. Document mutated
       │
7. ValidationEngine cache becomes stale (document changed)
       │
8. Next validation request returns a fresh snapshot
       │
9. Fixed issue no longer present
```

Auto Fix does not trigger validation directly. The document mutation marks the validation cache stale (per M3.5.1). The next consumer to request validation gets a fresh snapshot. This keeps Auto Fix decoupled from the validation lifecycle — exactly like every other document mutation in the editor.

---

## 7. Fix Scope

| Fix Type | Example | Commands |
|---|---|---|
| Structural | Connect disconnected road | `road.connect` |
| Creation | Create missing entrance | `entrance.create` |
| Assignment | Assign missing QR code | `entity.setMetadata` |
| Deletion | Remove duplicate vertices | `geometry.clean` |
| Bulk | Fix all overlapping rooms | Multiple `geometry.move` per issue |

A single `FixProvider` may produce multiple commands for one issue. A bulk fix (Fix all) collects one `FixResult` per issue and dispatches them as a single composite command — one undo, one history entry.

---

## 8. Non-Goals (M3.5.4)

- Auto-fix execution inside `ValidationEngine` (engine never mutates)
- AI-generated fixes or recommendations
- Interactive fix wizards (multi-step UI)
- Persistent fix history beyond the document's command history
- Automatic fix on validation (fixes are always user-triggered)

---

## 9. Completion Criteria

M3.5.4 is complete when:

1. `FixProvider` interface exists with `fixId`, `label`, `canApply()`, `buildCommands()`, and optional `priority` + `buildPreview()`.
2. `AutoFixRegistry` registers and retrieves fixes by `fixId`, resolving priority ties last-wins.
3. `FixProviderModule` registers fixes boot-only via `registerFixes()` (mirrors `RuleProvider`).
4. Fixes return `FixResult` (commands + optional message + optional confirmation), consumed by `CommandDispatcher` — no direct document mutation.
5. Problems Panel shows a Fix button when `issue.fixId` maps to a registered provider.
6. Fix button is disabled when `canApply()` returns false.
7. Clicking Fix dispatches the provider's commands through `CommandDispatcher`.
8. Fix all dispatches a single composite command (one undo, one history entry).
9. Fixes are undoable via the normal command history.
10. Auto Fix does not trigger validation — document change marks the cache stale.
