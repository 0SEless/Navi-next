# P1.1 — Single Building Authoring Workflow

## Objective

Prove the administrator workflow end-to-end: an administrator with no existing data can author a single building and publish it to the Runtime.

This is the first product-phase milestone. It replaces the architecture-era "M3.x Studio" framing with a user-ability test: **can an administrator complete a real task from start to finish?**

## Success Criteria

1. Create a campus with a name and metadata.
2. Draw the campus boundary.
3. Add one building with a name.
4. Upload and calibrate one floor plan image.
5. Trace 5 rooms on that floor.
6. Trace hallways connecting the rooms.
7. Place entrances on the building.
8. Run validation until there are no blocking errors.
9. Publish successfully.
10. Open the published output in the Runtime verification page and navigate between two rooms.

## What Must Be Built or Fixed

### 1. Floor Plan Upload UI (new)

**Problem:** The data model supports `planImageId` on floors, but there is no UI to upload an image and link it to a floor.

**Requirements:**
- An "Upload Floor Plan" button in the Floor Editor toolbar
- A file picker accepting image files (PNG, JPEG)
- On upload, the image appears on the canvas as an overlay via `ImageSource.updateImage()`
- The uploaded image persists with the saved campus document
- A calibration mode where the administrator clicks two points on the image and maps them to real-world coordinates (reuses `CalibrationEngine` from `@navi/editor`)

**Files to touch:**
- `src/components/floor-editor/FloorEditor.tsx` — add upload button
- `src/components/floor-editor/FloorEditorCanvas.tsx` — render uploaded floor plan
- Possibly a new `FloorPlanUploader` component or hook

**Acceptance:**
- Administrator can upload a floor plan image
- Image renders on the canvas at the correct position
- Calibration maps image pixels to building-local coordinates
- The floor plan survives save → reload

### 2. Validation Results Panel (new)

**Problem:** `ValidationEngine` can validate a document, but no UI displays the results to the administrator.

**Requirements:**
- After validation runs (manual or on-save), show results in a panel or dialog
- Display categorized errors and warnings
- Highlight which steps of the workflow are blocked
- Auto-fix suggestions where available

**Files to touch:**
- Possibly a new `ValidationPanel` component
- `StudioWorkspace.tsx` or toolbar to trigger validation
- Wire `WorkflowService.validate()` to the UI

**Acceptance:**
- Administrator can trigger validation
- Errors are displayed with actionable messages
- Blocking errors prevent publish

### 3. Tool Verification (test/fix only)

**Problem:** The room tracing, hallway tracing, and entrance placement tools exist but have not been tested end-to-end through the UI.

**Requirements:**
- Manual verification that each tool completes its drawing session and produces correct entities
- Fix any bugs discovered during verification

**Files to touch:**
- Bug fixes only — no architecture changes

**Acceptance:**
- Administrator can trace 5 rooms on a floor plan
- Administrator can trace a hallway connecting rooms
- Administrator can place an entrance on the building

### 4. Publish Button Integration (verify only)

**Problem:** The Publish button exists in `StudioToolbar` but the end-to-end flow through validation → compilation → manifest generation → artifact storage has not been tested from the UI.

**Requirements:**
- Verify that clicking Publish runs the full pipeline
- Verify the manifest appears in the publish output directory
- Verify the published bundle can be consumed by the Runtime demo page

**Files to touch:**
- Verification only — no code changes expected

**Acceptance:**
- Publish produces a valid manifest with `schemaVersion: 1`
- Runtime loads the published bundle at `/demo/navigate`
- Search finds rooms in the published data
- Route between two rooms displays correctly

## Non-Goals

- Multiple buildings (P1.2)
- Multiple floors (P1.2)
- Campus roads (P1.3)
- QR markers (P1.4)
- Panoramas (P1.5)
- Stairs and elevators (P1.2)
- Performance optimization
- Mobile layout
- Keyboard shortcuts
- Undo/redo improvements beyond what already exists
- Any new architecture, services, registries, or abstractions

## Risk Register

| Risk | Likelihood | Mitigation |
|------|-----------|------------|
| Floor plan upload requires backend storage | Medium | Store images as base64 in the document or use local filesystem for the MVP |
| Calibration UI is complex | Medium | Reuse existing `CalibrationEngine`; limit to 2-point affine calibration |
| Tool bugs block the workflow | Medium | Verify each tool early; fix on discovery |
| Validation engine has rule gaps | Low | Only require that existing rules pass for the single building case |
| Publish output doesn't match Runtime expectations | Low | Already verified by walking skeleton test |

## Design Principles Applied

- **The administrator workflow is the backbone** — every piece of work in this milestone exists to unblock the next step in the workflow
- **The visitor route is the test** — the final success criterion is a working route in the Runtime, not a clean editor state
- **Real data before polish** — wire the tools together before improving their UX
- **No new architecture** — all existing systems are sufficient; this milestone only adds UI surfaces

## Upstream Dependencies
