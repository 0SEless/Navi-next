# M3.5.5 — Incremental Validation

**Status:** Accepted
**Date:** 2026-07-12
**Dependencies:** M3.5.1 (Validation Engine), M3.5.2 (Rule Framework)

---

## 1. Purpose

Full validation re-runs every rule on every entity. For large campuses this is wasteful — most edits affect a single entity or type. Incremental validation skips rules and analysis passes whose inputs haven't changed, reducing validation time to a constant fraction of the full run.

---

## 2. Strategy

Incremental validation does not change the ValidationEngine's public API or the rule interface. It is an internal optimization of the pipeline defined in M3.5.1.

### Granularity

Entity-type level. When a room is edited, only rules that inspect rooms re-run. Graph rules (which depend on the full graph) always re-run. This is coarser than per-entity tracking but avoids the complexity of field-level dependency graphs.

### Flow

```
validate(document, profile)
        │
        ▼
┌─────────────────────────────┐
│  1. Version check            │
│     (same as M3.5.1)         │
└─────────────────────────────┘
        │
        ▼
┌─────────────────────────────┐
│  2. Compute changes          │
│     Which entity types       │
│     were added/updated/      │
│     deleted since last run?  │
└─────────────────────────────┘
        │
        ▼
┌─────────────────────────────┐
│  3. Filter analysis passes   │
│     Skip passes whose        │
│     inputs haven't changed   │
└─────────────────────────────┘
        │
        ▼
┌─────────────────────────────┐
│  4. Filter rules             │
│     Skip rules whose         │
│     entity types unchanged   │
└─────────────────────────────┘
        │
        ▼
┌─────────────────────────────┐
│  5. Build snapshot           │
│     Merge old + new issues,  │
│     carry forward old        │
│     analysis results         │
└─────────────────────────────┘
```

## 3. Change Detection

The engine needs to know what changed between validation runs. It queries the document for entity change metadata.

### ValidationAffinity

```typescript
type ValidationAffinity =
  | 'room'
  | 'building'
  | 'road'
  | 'floor'
  | 'entrance'
  | 'stairs'
  | 'elevator'
  | 'asset'
  | 'graph'
  | 'global'
```

Rules and analysis passes declare their affinity using this set. `'global'` means the pass always runs. A future entity type is added by extending this union — typos become compile errors rather than silent optimization bugs.

### EntityChange

```typescript
type EntityOperation = 'added' | 'updated' | 'deleted'

interface EntityChange {
  readonly entityId: string
  readonly entityType: ValidationAffinity
  readonly operation: EntityOperation
}
```

The engine reduces `EntityChange[]` to entity types internally. Storing the full change list preserves diagnostic information without changing the filtering algorithm.

### Source of Change Data

The `CampusDocument` exposes a method:

```typescript
class CampusDocument {
  /** Return entity changes since the given document version. */
  getChangesSince(version: number): ReadonlyArray<EntityChange>
}
```

The engine calls `document.getChangesSince(lastValidatedVersion)` at the start of `validate()`. If the version matches, there's nothing to do (return cache). If it differs, the engine reduces changes to entity types and filters accordingly.

### When Full Re-Validation Is Required

| Condition | Action |
|---|---|
| No changes since last run | Return cached snapshot |
| Entity type changed | Run rules + analyses for that type |
| Profile changed | Full re-validation |
| Structural change (graph-level) | Full re-validation |
| `validateFresh()` called | Full re-validation |

## 4. Rule Affinity

Each rule declares which entity types it cares about. Rules that inspect the entire document (graph connectivity, campus boundary) declare `'global'` affinity — they always run.

```typescript
interface ValidationRule {
  readonly ruleId: string
  readonly category: string
  readonly defaultSeverity: 'error' | 'warning' | 'info'
  readonly profiles: ReadonlyArray<string>

  /**
   * Entity types this rule inspects.
   * 'global' = always runs (global rule like graph connectivity).
   */
  readonly affinity: ReadonlyArray<ValidationAffinity>

  execute(context: ValidationContext): ReadonlyArray<ValidationIssue>
}
```

### Affinity Rules

| Affinity | Behavior |
|---|---|
| `['room']` | Runs only when any room is added, updated, or deleted |
| `['room', 'building']` | Runs when rooms or buildings change |
| `['global']` | Always runs (global rules) |

### Example

```typescript
class DisconnectedGraphRule implements ValidationRule {
  readonly ruleId = 'graph.disconnected'
  readonly category = 'graph'
  readonly defaultSeverity = 'error'
  readonly profiles = ['draft', 'publish', 'strict']
  readonly affinity = ['global']  // Always runs — graph depends on everything
}

class OverlappingRoomsRule implements ValidationRule {
  readonly ruleId = 'geometry.overlapping'
  readonly category = 'geometry'
  readonly defaultSeverity = 'error'
  readonly profiles = ['publish', 'strict']
  readonly affinity = ['room']  // Only runs when rooms change
}
```

### Invariant: Rule Owns Its Issues

Each rule completely owns the issues it produces. When a rule re-runs, **all** of its previous issues are discarded before the new issues are added. No merging, no diffing, no partial updates.

```
Rerun Rule A
  → delete all issues where issue.ruleId === 'A'
  → add new issues from Rule A
```

The engine tracks which rule produced each issue via `issue.ruleId`. Ownership is by `ruleId`. This prevents two rules from ever contributing to the same issue, and keeps issue replacement as a simple set operation.

## 5. Analysis Pass Affinity

Analysis passes also declare affinity. Passes with `['global']` always run.

```typescript
interface AnalysisPass<T> {
  readonly produces: string
  readonly description: string
  readonly affinity: ReadonlyArray<ValidationAffinity>

  execute(document: CampusDocument): T
}
```

### Built-in Pass Affinity

| Pass | Affinity | Rationale |
|---|---|---|
| Graph Analysis | `['road', 'entrance', 'stairs', 'elevator', 'hallway']` | Only graph-traversable entities affect connectivity |
| Geometry Analysis | `['room', 'building']` | Only spatial entities affect geometry |
| Metadata Index | `['room', 'building', 'floor']` | Only named/coded entities |
| Spatial Index | `['room', 'building']` | Only spatial entities |

Graph Analysis does **not** run on metadata-only edits (room name, room code). Changing a room name does not restructure the navigation graph, so graph recomputation is skipped.

---

## 6. Execution

### Analysis Passes

```
filterAnalysisPasses(changes):

  for each pass in registeredPasses:
    if pass.affinity includes 'global' → always run
    else if any change type overlaps pass.affinity → run
    else → skip, carry forward old result
```

### Rules

```
filterRules(changes, profile):

  for each rule in registeredRules:
    if rule.profiles doesn't include profile → skip
    if rule.affinity includes 'global' → always run
    else if any change type overlaps rule.affinity → run
    else → skip
```

### Snapshot Merge

The new snapshot is assembled as:

```
New Snapshot
  = Previous Snapshot
    − outputs of rerun rules
    − outputs of rerun analyses
    + new outputs
```

Concretely:

1. Start with previous snapshot's issues and analysis cache
2. Remove all issues where `issue.ruleId` belongs to a re-run rule
3. Remove analysis results for re-run passes
4. Add new analysis results from re-run passes
5. Add new issues from re-run rules
6. Build final snapshot from the merged set

```typescript
const newSnapshot = buildSnapshot({
  issues: [...previousSnapshot.issues.filter(i => !rerunRuleIds.has(i.ruleId)), ...freshIssues],
  analysisCache: { ...previousSnapshot.analysisCache, ...freshAnalyses },
})
```

Rules that re-run fully replace their issue contribution. Rules that didn't re-run are unaffected. This preserves the rule-owns-its-issues invariant.

## 7. Edge Cases

| Situation | Handling |
|---|---|
| Entity deleted, rule affinity matches | Rule runs (deletion affects validity) |
| Entity added with new type | Affected rules run |
| First validation | Full run (no previous snapshot) |
| Profile switch | Full run (previous snapshot uses different profile) |
| No changes but forced | `validateFresh()` bypasses all filtering |

---

## 8. Performance Expectations

Incremental validation should make the common case (single entity edit) run in constant time relative to campus size:

| Scenario | Validation Run |
|---|---|
| First load | All rules + analyses |
| Edit room name | Metadata index + metadata rules only |
| Move room | Spatial index + geometry rules only |
| Add building | Graph analysis + all building/room rules |
| No changes | Cached snapshot, no re-run |

The exact scope depends on the rule/analysis affinity split, but the principle holds: edit one entity type → validate that type's rules + analyses.

---

## 9. Non-Goals (M3.5.5)

- Field-level change tracking (entity-type granularity is sufficient for M3.5)
- Distributed or parallel rule execution
- Rule result caching beyond the current snapshot
- Change tracking at the command level (the document owns change data)

---

## 10. Completion Criteria

M3.5.5 is complete when:

1. `ValidationRule.affinity` exists using `ValidationAffinity` typed values — rules declare which entity types they inspect.
2. `AnalysisPass.affinity` exists using `ValidationAffinity` typed values — passes declare which entity types they inspect.
3. `CampusDocument.getChangesSince(version)` returns `EntityChange[]` with entity ID, type, and operation.
4. `'global'` affinity means the rule/pass always runs.
5. Rules completely own their issues — re-running a rule discards all its previous issues.
6. Analysis passes with no overlapping changes carry forward results from the previous snapshot.
7. Rules with no overlapping changes carry forward issues from the previous snapshot.
8. `validateFresh()` bypasses all affinity filtering.
9. Full re-validation still produces an identical snapshot to incremental (determinism preserved).
10. Snapshot merge follows `Previous − rerun outputs + new outputs`.

## 11. Validation Epoch

The engine maintains a monotonically increasing `validationEpoch` counter, incremented on every validation run (including fresh and incremental).

```typescript
interface ValidationSnapshot {
  readonly epoch: number  // monotonically increasing per validation run
  // ... other fields
}
```

### Purpose

`document.version` identifies document state. `validationEpoch` identifies validation state. They are independent:

- Two validations of the same document version with different profiles are different epochs.
- Two validations of the same document version with the same profile (one full, one incremental) may be different epochs if the snapshot differs.

Consumers (Problems Panel, Workflow Card, Publish) can display or compare `epoch` to know whether they're looking at the latest validation result — without comparing issue lists.

### Generated By

The engine increments `epoch` inside `validate()` and `validateFresh()` before caching the snapshot. Consumers never set it.
