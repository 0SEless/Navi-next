# M3.5.3 — Problems Panel

**Status:** Accepted
**Date:** 2026-07-12
**Dependencies:** M3.5.1 (Validation Engine), M3.4.4 (Context Panel), CommandDispatcher, Selection, Camera

---

## 1. Purpose

The Problems Panel is a dedicated workspace panel that displays validation issues. It is the primary user-facing surface of the validation system. Its purpose is to answer "what's wrong with my project?" and let users navigate directly to each problem.

---

## 2. Architecture

```
ValidationEngine
       │
       ├── getLastSnapshot() ← Problems Panel reads on mount
       │
       └── validation.updated ← Problems Panel subscribes
                │

┌──────────────────────────┐
│     Problems Panel        │
│                           │
│  ┌─ Errors (3) ────────┐ │
│  │ • Disconnected road  │ │
│  │ • Missing entrance   │ │
│  │ • Overlapping rooms  │ │
│  └──────────────────────┘ │
```

## 3. Panel Registration

The Problems Panel registers as a workspace panel through `PanelRegistry`, using a dedicated kind string:

```typescript
panelRegistry.registerPanel('problems', ProblemsPanel)
```

This distinguishes it from entity editors (`PanelRegistry.registerEditor()`) and the Context Panel (`context` kind). It appears as a sibling to the Context Panel, not a replacement.

### Workspace Layout

```
┌──────────────────────────────────────────────┐
│  Canvas                                       │
│                                               │
└──────────────────────────────────────────────┘
┌──────────────────┬───────────────────────────┐
│  Context Panel    │  Problems Panel            │
│  (entity editor)  │  (issues list)             │
└──────────────────┴───────────────────────────┘
```

The Problems Panel is collapsed by default and expands when issues are detected. Users can also open it manually via a toolbar button or the `?` help overlay.

## 4. Data Flow

### Reading Validation State

```typescript
function ProblemsPanel() {
  const engine = useService('validationEngine')
  const [snapshot, setSnapshot] = useState(engine.getLastSnapshot())

  // Subscribe to validation updates
  useEffect(() => {
    const sub = engine.onValidationUpdated(s => setSnapshot(s))
    return () => sub.unsubscribe()
  }, [])
}
```

### Refresh Model

| Trigger | Action |
|---|---|
| Panel mounts | Call `engine.getLastSnapshot()` |
| `validation.updated` event | Replace snapshot, re-render |
| Document changes | Show stale indicator |
| User clicks stale indicator | `dispatcher.execute('validation.run')` |

The panel never calls `validate()` or `validateFresh()` directly. Re-validation is triggered through the command system, keeping the UI layer decoupled from the service layer. The panel is a consumer, not a controller.

### Auto-Expand Behavior

The panel expands automatically only when transitioning from zero issues to one or more:

```
if (previousSnapshot.issues.length === 0 && newSnapshot.issues.length > 0)
  → expand panel
```

This prevents constant expansion on every incremental validation update.

## 5. Issue Display

### Grouping

Issues are grouped by severity, then by category within each severity:

```
Errors (3)
  ├── Graph
  │   └── Disconnected road (Building A → Building B)
  ├── Geometry
  │   └── Overlapping rooms (Room 101, Room 102)
  └── Accessibility
      └── Missing entrance (Building A)

Warnings (2)
  ├── Metadata
  │   └── Missing name (Room 103)
  └── Metadata
      └── Duplicate room number (Room 104, Room 105)
```

### Issue Entry

Each issue entry displays:

```
[severity icon] [message]
                 [entity type: name] [location: x, y]
```

- Severity icon: red circle (error), yellow triangle (warning), blue info (info)
- Message from `ValidationIssue.message`
- Entity type and name below the message (if targets available)
- Click to select + focus

### Issue Identity

Every `ValidationIssue` has a stable `issueId` that remains consistent across validation runs. The problem panel uses `issueId` as the React key and selection identifier — never index-based positioning.

### Ordering

Issues are sorted deterministically to prevent UI jumping:

```
1. By severity: error → warning → info
2. By category: alphabetical
3. By message: alphabetical
4. By first target entity name: alphabetical
```

This ordering is defined once in the panel. The snapshot does not guarantee order — the panel enforces it.

### Empty State

When the snapshot has no issues, the panel shows:

```
✓ No problems detected
```

or for the current profile:

```
✓ Campus is valid for {profile} profile
```

### Stale Indicator

When `document.version > snapshot.documentVersion`, a banner appears:

```
⚠ Document changed since last validation. [Re-validate]
```

Clicking re-validate dispatches `validation.run` through the command system.

## 6. Issue Navigation

Clicking an issue triggers a multi-step interaction:

```
1. Click issue in Problems Panel
       │
2. SelectionManager.select(targets)
       │
3. Camera.focus(location || first target's center)
       │
4. Context Panel updates to show first target's editor
```

### Selection Behavior

| Targets | Selection |
|---|---|
| Single entity | Select that entity |
| Multiple entities | Select all (multi-select) |
| No targets | Focus camera on issue location only |

This reuses the `SelectionManager` from M3.4.2 and the `Camera` focus system. No new selection or camera logic is introduced.

### Invariant

**Problems Panel never renders property editors.** Navigation ends at selection + focus. The Context Panel renders the editor. If the Problems Panel later displays inline details for an issue, those details are read-only — no form inputs, no mutation controls, no inline editing.

---

## 7. Integration Points

| Integration | Mechanism |
|---|---|
| `PanelRegistry` | `registerPanel('problems', ProblemsPanel)` |
| `ValidationEngine` | `getLastSnapshot()`, `validateFresh()`, `onValidationUpdated()` |
| `SelectionManager` | `select(entityIds)` |
| `Camera` | `focus(point)` |
| `ContextResolver` | Selection change triggers context re-resolution |

The Problems Panel is a consumer of these services. It does not own any of them.

---

## 8. Panel Props

```typescript
interface ProblemsPanelProps {
  // Filter issues to a specific entity (optional, used from Context Panel)
  entityFilter?: string

  // Filter issues to a specific category (optional)
  categoryFilter?: string
}
```

These props allow the Context Panel or toolbar to pre-filter the issue list. For example, selecting an entity and viewing "Problems for this entity" shows only issues targeting that entity.

### Future Filters

A `severityFilter` prop is anticipated for workflows like "Show errors only" or "Hide info." It is not included in M3.5.3 to avoid over-engineering before user feedback confirms the need.

---

## 9. Non-Goals (M3.5.3)

- Auto-fix buttons in the panel (→ M3.5.4)
- Visual overlays on the canvas showing issue locations (post-M3.5)
- Editing or dismissing issues
- User-configurable severity overrides
- Real-time issue count in the panel tab

---

## 10. Completion Criteria

M3.5.3 is complete when:

1. Problems Panel is registered in `PanelRegistry` as a `'problems'` panel.
2. Panel displays issues grouped by severity, then by category.
3. Panel shows empty state when no issues exist.
4. Panel shows stale indicator when `document.version > snapshot.documentVersion`.
5. Clicking an issue selects the entity and focuses the camera.
6. Panel refreshes when `validation.updated` is emitted.
7. `entityFilter` and `categoryFilter` props work for scoped views.
8. No new selection, camera, or validation logic lives in the panel — it only consumes existing services.
9. Panel is collapsed by default; auto-expands only on 0→issues transition.
10. **Re-validation is triggered through the command system** (`dispatcher.execute('validation.run')`), not by calling `validateFresh()` directly.
11. **Issue ordering is deterministic** — sorted by severity → category → message → entity name.
12. Each issue uses its stable `issueId` as the React key.
13. Problems Panel never renders property editors — navigation ends at selection + focus.
