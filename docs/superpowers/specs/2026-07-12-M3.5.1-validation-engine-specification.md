# M3.5.1 — Validation Engine

**Status:** Accepted
**Date:** 2026-07-12
**Dependencies:** M3.5 Vision, CampusDocument

---

## 1. Purpose

The Validation Engine is the core service that answers "is this document valid?" It produces a reusable `ValidationSnapshot` that becomes the canonical validation state of `CampusDocument`. Every validation consumer — Problems Panel, Workflow Card, Publish — reads from the same snapshot.

---

## 2. Service Design

```typescript
class ValidationEngine extends BaseEditorService {
  readonly id = 'validationEngine'
  readonly dependencies: readonly string[] = []

  /**
   * Validate a document against the given profile.
   * Returns the cached snapshot if up-to-date, otherwise runs validation.
   */
  validate(document: CampusDocument, profile?: string): ValidationSnapshot

  /**
   * Force re-validation regardless of cache state.
   */
  validateFresh(document: CampusDocument, profile?: string): ValidationSnapshot

  /**
   * Return the current cached snapshot, or undefined if none exists.
   */
  getLastSnapshot(): ValidationSnapshot | undefined

  /**
   * Subscribe to validation updates. Called after every validation run.
   * Returns an unsubscribe function.
   */
  onValidationUpdated(cb: (snapshot: ValidationSnapshot) => void): () => void
}
```

### Cache Logic

The engine emits `validation.updated` after each validation run. This is an output-only event — consumers react, but the engine does not depend on them.

```typescript
class ValidationEngine extends BaseEditorService {
  private _snapshot: ValidationSnapshot | undefined
  private _listeners: Set<(snapshot: ValidationSnapshot) => void> = new Set()

  validate(document: CampusDocument, profile?: string): ValidationSnapshot {
    const resolvedProfile = profile ?? 'default'
    if (this._snapshot
        && this._snapshot.documentVersion === document.version
        && this._snapshot.profile === resolvedProfile) {
      return this._snapshot
    }

    this._snapshot = this.runValidation(document, resolvedProfile)
    this._emit()
    return this._snapshot
  }

  validateFresh(document: CampusDocument, profile?: string): ValidationSnapshot {
    const resolvedProfile = profile ?? 'default'
    this._snapshot = this.runValidation(document, resolvedProfile)
    this._emit()
    return this._snapshot
  }

  getLastSnapshot(): ValidationSnapshot | undefined {
    return this._snapshot
  }

  onValidationUpdated(cb: (snapshot: ValidationSnapshot) => void): () => void {
    this._listeners.add(cb)
    return () => this._listeners.delete(cb)
  }

  private _emit(): void {
    if (this._snapshot) {
      this._listeners.forEach(cb => cb(this._snapshot!))
    }
  }
}
```

There is only one cache invalidation mechanism: `document.version`. No dirty flag, no event subscriptions, no synchronization. If the version matches, the snapshot is current. This keeps the engine almost stateless — `_snapshot` is the only mutable field.

The engine never calls `validate()` autonomously. Consumers decide when to pull, preventing wasted validation when no panel is visible.

## 3. ValidationSnapshot

The single source of truth for validation state. Immutable — once constructed, its contents never change.

```typescript
interface ValidationSnapshot {
  /** Monotonically increasing per validation run. */
  readonly epoch: number

  /** Identity — ties snapshot to a specific document state. */
  readonly documentId: string
  readonly documentVersion: number
  readonly profile: string
  readonly validatedAt: DOMHighResTimeStamp

  /** Overall document health. */
  readonly state: 'valid' | 'warnings' | 'errors'

  /** All issues found, ordered by severity then location. */
  readonly issues: ReadonlyArray<ValidationIssue>

  /** Summary statistics and timing. */
  readonly statistics: ValidationStatistics

  /** Cached analysis results consumed by rules. */
  readonly analysisCache: AnalysisCache
}
```

### ValidationIssue

```typescript
interface ValidationIssue {
  readonly issueId: string
  readonly ruleId: string
  readonly severity: 'error' | 'warning' | 'info'
  readonly message: string

  /** The entity or entities this issue relates to. */
  readonly targets: ReadonlyArray<{
    entityId: string
    entityType: string
  }>

  /** Optional location on the canvas for camera focus. */
  readonly location?: { x: number; y: number }

  /** Reference to a registered auto-fix, if available. */
  readonly fixId?: string
}
```

### ValidationStatistics

```typescript
interface ValidationStatistics {
  readonly duration: number
  readonly totalIssues: number
  readonly errors: number
  readonly warnings: number
  readonly infos: number
  readonly rulesExecuted: number
  readonly rulesPassed: number
  readonly rulesFailed: number
}
```

### AnalysisCache

```typescript
interface AnalysisCache {
  readonly graph?: GraphAnalysis
  readonly geometry?: GeometryAnalysis
  readonly metadata?: MetadataIndex
  readonly spatial?: SpatialIndex
}
```

These are computed once per validation run and shared across all rules. Each analysis pass is a pure function:

```typescript
type AnalysisPass<T> = (document: CampusDocument) => T
```

Analysis results live in the snapshot. If the document hasn't changed, the entire snapshot (including analyses) is reused.

## 4. Validation Pipeline

```
validate(document, profile)
        │
        ▼
┌───────────────────┐
│  1. Gate check    │  dirty? version match? profile match?
│                   │  → skip if cached
└────────┬──────────┘
         │
         ▼
┌───────────────────┐
│  2. Analysis      │  Run all registered analysis passes
│     Passes        │  GraphAnalysis, GeometryAnalysis, etc.
│                   │  Store results in ValidationAnalyses
└────────┬──────────┘
         │
         ▼
┌───────────────────┐
│  3. Rule          │  For each registered rule:
│     Execution     │    a. Check if rule's profiles include requested profile
│                   │    b. If yes → run rule(document, analyses)
│                   │    c. Collect issues
└────────┬──────────┘
         │
         ▼
┌───────────────────┐
│  4. Build         │  Aggregate issues, compute statistics
│     Snapshot      │  Cache result
└───────────────────┘
```

### Threading Model

The ValidationEngine exposes a synchronous API. Internally, analysis passes could run on a Web Worker in the future, but the public `validate()` interface remains synchronous via caching.

A future optimization could run analysis passes on a Web Worker, but the interface remains synchronous.

## 5. Cache Ownership

- `ValidationEngine` owns the single cached `ValidationSnapshot`
- Every consumer reads from `ValidationEngine.getLastSnapshot()` or calls `validate()`
- No consumer caches its own issue list
- When the document version changes, the engine returns a fresh snapshot on next `validate()` call
- The previous snapshot object remains valid until replaced — consumers may display stale data until they re-validate

### Cache Invalidation Rules

| Condition | Effect |
|---|---|
| `snapshot.documentVersion !== document.version` | Re-validate |
| `snapshot.profile !== requestedProfile` | Re-validate |
| `validateFresh()` called | Always re-validate |
| Version + profile match | Return cached |

---

## 7. Determinism

Validation is a pure function of document state + profile + configuration:

```typescript
// Same inputs → same output, always
const a = engine.validate(document, 'publish')
const b = engine.validate(document, 'publish')
assert(a.issues === b.issues)  // deep equal
```

This means:
- No dependence on editor state, tool context, or UI
- Tests can assert on snapshot structure
- Snapshots can be serialized and compared
- Caching is safe — no hidden state can produce different results

---

## 8. Relationship to M3.5.5 (Incremental Validation)

M3.5.1 defines the full-validation pipeline. M3.5.5 optimizes it by:

1. Tracking which rules are affected by which entity types
2. Running only affected rules when the document changes
3. Reusing analysis results for unchanged document regions

M3.5.5 extends the pipeline defined here. The core design — single snapshot, pull-based API, deterministic rules — remains unchanged.

## 10. Completion Criteria

M3.5.1 is complete when:

1. `ValidationEngine` is implemented with `validate()`, `validateFresh()`, and `getLastSnapshot()`.
2. `ValidationSnapshot` includes `epoch`, `documentId`, `documentVersion`, `profile`, `validatedAt`, `state`, `issues`, `statistics`, and `analysisCache`.
3. `validate()` returns cached snapshot when `document.version` and `profile` match.
4. `validateFresh()` always re-runs validation.
5. `ValidationSnapshot` is immutable — all fields are `readonly`, no setters or mutators.
6. `state` correctly reflects overall document health: `'valid'` (no issues), `'warnings'` (warnings only), `'errors'` (any error).
7. Each `ValidationIssue` has a unique `issueId`.
8. Validation produces identical snapshots for identical inputs (deterministic).
9. Analysis passes run before rules and results are stored in `analysisCache`.
10. `onValidationUpdated()` emits the new snapshot after every validation run.
11. No consumer creates its own validation cache (enforced by convention).
