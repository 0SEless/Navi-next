## 1. Purpose

Phase 5A proves the entire Auto Fix pipeline with the minimum possible code. It implements the infrastructure (`AutoFixRegistry`, `FixProvider`, Problems Panel integration) and exactly one real fix.

If this loop works, the Auto Fix architecture is validated and all future fixes become provider additions — not infrastructure work.

---

## 2. Vertical Slice

Only one fix is implemented in Phase 5A:

| Rule | Issue | Fix | Commands |
|------|-------|-----|----------|
| `metadata.missing-name` | Entity has empty name | Assign `"Untitled"` | `entity.setMetadata` |

This fix is chosen because:
- Zero spatial or graph logic required
- The fix is deterministic — same issue always produces the same command
- The fix is idempotent — if name is already set, `canApply()` returns false
- Verifies undo/revalidation cleanly — fix → issue gone → undo → issue returns

---

## 3. Quality Contract

Every `FixProvider` MUST satisfy these four properties:

| Property | Meaning | How Missing Name satisfies it |
|----------|---------|------------------------------|
| **Deterministic** | Same issue + document → equivalent commands | Always assigns `"Untitled"` |
| **Atomic** | One user action → one undo entry | Produces one `entity.setMetadata` command |
| **Idempotent** | Already-resolved fix has no effect | `canApply()` checks name is empty; if already named, returns false |
| **Self-validating** | After execution, next validation removes the issue | `metadata.missing-name` rule passes when name is non-empty |

These are acceptance criteria for every fix provider added in future phases.

---

## 4. Principle: FixProviders Never Decide Policy

The boundary between validation and fixing must remain strict:

- `ValidationRule` decides **what is wrong**
- `FixProvider` decides **how to resolve that specific wrong**

A fix provider MUST NOT:
- Perform extra validation beyond checking preconditions
- Invent new business rules or override existing ones
- Search the document for issues (it receives the issue that triggered it)

**Example — correct separation:**

```typescript
// ValidationRule decides WHAT is wrong
class MissingNameRule implements ValidationRule {
  execute(context: ValidationContext): ValidationIssue[] {
    return context.document.entities
      .filter(e => !e.name)
      .map(e => ({ fixId: 'metadata.assign-name', targets: [{ entityId: e.id }], ... }))
  }
}

// FixProvider decides HOW to fix that specific wrong
class AssignUntitledFix implements FixProvider {
  canApply(issue, ctx) { return ctx.document.getEntity(issue.targets[0].entityId)?.name === '' }
  buildCommands(issue, ctx) {
    return { commands: [{ id: 'entity.setMetadata', payload: { entityId: issue.targets[0].entityId, name: 'Untitled' } }] }
  }
}
```

This preserves the clean boundary established in the Architecture Baseline.

### 6.3 AssignUntitledFix (the only concrete fix in Phase 5A)

```typescript
class AssignUntitledFix implements FixProvider {
  readonly fixId = 'metadata.assign-name'
  readonly label = 'Assign "Untitled"'
  readonly priority = 0

  canApply(issue: ValidationIssue, context: FixContext): boolean {
    const entity = context.document.getEntity(issue.targets[0]?.entityId)
    return entity != null && entity.name === ''
  }

  buildCommands(issue: ValidationIssue, context: FixContext): FixResult {
    return {
      commands: [{
        type: 'entity.setMetadata',
        payload: {
          entityId: issue.targets[0].entityId,
          name: 'Untitled',
        },
      }],
      message: 'Assigned name "Untitled"',
    }
  }
}
```

## 7. Integration Flow

```
ValidationEngine.validate(document)
        │
        ▼
ValidationSnapshot.issues[].fixId = 'metadata.assign-name'
        │
        ▼
ProblemsPanel renders issue with Fix button
        │
        ▼
User clicks Fix
        │
        ▼
ProblemsPanel resolves:
  autoFixRegistry.getFix('metadata.assign-name') → AssignUntitledFix
        │
        ▼
fix.canApply(issue, context) → checks entity name is empty
        │
        ▼
fix.buildCommands(issue, context) → [{ type: 'entity.setMetadata', payload }]
        │
        ▼
dispatcher.execute(command)
        │
        ▼
CampusDocument updated (name set to "Untitled")
        │
        ▼
ValidationEngine cache stale (document version changed)
        │
        ▼
Next validation request → fresh snapshot → issue absent
        │
        ▼
Fix button disappears (no issue to show)
```

## 8. Fix Button in Problems Panel

### 8.1 Single issue

```
[error icon] [Entity "C-1" is missing a name]
             [Room: Corridor 1F]
             [+Fix]     ← only if fixId registered & canApply()
```

Clicking Fix:
1. Reads `issue.fixId` → looks up provider via `autoFixRegistry.getFix()`
2. Calls `provider.canApply(issue, context)` — if false, button disabled
3. Calls `provider.buildCommands(issue, context)` → `FixResult`
4. Calls `dispatcher.execute(...result.commands)`

### 8.2 Fix All (group header)

Group header shows Fix All if any issue in the group has an applicable fix.

Clicking Fix All:
1. Iterates all issues in the group
2. For each issue with the same `fixId` and `canApply()`, collects commands
3. Dispatches a single composite command (one undo entry)

## 9. Completion Criteria

Phase 5A is complete when:

1. `FixProvider` interface exists with `fixId`, `label`, `canApply()`, `buildCommands()`, optional `priority` + `buildPreview()`.
2. `AutoFixRegistry` registers and retrieves fixes by `fixId`, resolves priority ties last-wins with warning.
3. `AssignUntitledFix` registers via `FixProviderModule` and handles `metadata.missing-name` issues.
4. Problems Panel shows a Fix button when `issue.fixId` maps to a registered `FixProvider`.
5. Fix button is **disabled** when `canApply()` returns false.
6. Clicking Fix dispatches commands through `CommandDispatcher`.
7. Document is mutated after fix execution.
8. **Undo** restores the original state → issue reappears on revalidation.
9. **Redo** removes the issue again.
10. Fix All dispatches a single composite command (one undo entry for all fixes).
11. Auto Fix does **not** trigger validation — document mutation marks cache stale per M3.5.1.
12. The quality contract holds: deterministic, atomic, idempotent, self-validating.
13. No architectural changes beyond the listed files. No new managers, coordinators, or pipelines.

## 10. Non-Goals (Phase 5A)

- Graph fixes (Connect Road, Create Entrance) — deferred to Phase 5C
- Geometry fixes (overlap, self-intersection) — deferred to Phase 5C
- Multiple metadata fixes (QR, category) — deferred to Phase 5B
- Fix preview — deferred (optional `buildPreview()` interface exists but unused)
- Confirmation dialogs — deferred (`requiresConfirmation` flag exists but unused)
- Auto-fix on validation — always user-triggered
- Persistent fix history beyond document command history
- AI-generated or recommended fixes
